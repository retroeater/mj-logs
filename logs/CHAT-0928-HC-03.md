決定（平野さん、2026-09-28）

* 対象はチャンネルのライブすべて。カレンダーに載せるのは完全版（全編）の枠。完全版がメンバー限定で、一部だけ無料で見られる版もあるときは、説明欄にその無料版のリンクも載せる。
* 連盟の予定表は 2027-03-31 までの予定を対象にする（2027年4月以降の予定は、2026年12月末までに予定表に載る見込み）。予定表は Calendar API で読む。
* 予定表で1日にまとめて書かれた卓（「ベスト8AB卓」など）は、同じ放送枠で放送される。予定表から作った仮の予定は、同じ日・同じ大会の YouTube の枠が出たら、枠ごとの予定に切り替える。
* 表はスプレッドシート「ryoei.pro_日本プロ麻雀連盟_予定表」（`1elX7jZn86Ph8P2BRMdVSZClKhyDr_8_FFdS_saa1kCM`）の【1】元データ・【2】自動変換後・【3】手動補正を、/live と同じ3層として使う。書き込みは `live-channel-writer`（平野さんが共有済みと申告）。【2】【3】に掲載 Y/N を置き、【3】の行は日付＋件名で結び付ける。
* 予定表の予定に時刻が無いときは、過去の同じタイトル戦を参考に、【2】で開始時刻を仮置きする（例: 鳳凰戦 A2 → 16:00）。平野さんは【3】で上書きできる。
* 終了時刻は、同じ日に次の番組があればその開始時刻、無ければ 23:00 とする。例外は【3】で上書きする。放送後は実際の開始・終了時刻で上書きする。
* 件名は【3】手動補正を反映した題名。日の区別（決定戦の「二日目」など）は YouTube の題名から補い、【3】に行の無い枠は YouTube の題名を整えて使う。
* 今日以降の分を載せ、過去分は後で別に行う。同期は毎朝1回。カレンダーへの書き込みは既存のカレンダー用サービスアカウント（`GCP_SA_KEY`）。

### 手順2: 層1に項目を足す（commit 4470164d）

前提の確認: `build_record()` は `videos.list(part=snippet,contentDetails,liveStreamingDetails,status)` の応答から
`actualStartTime` だけを保存し、`scheduledStartTime`・`scheduledEndTime`・`actualEndTime`・`snippet.liveBroadcastContent` は保存していなかった（前提どおり）。

- `build_record()` に 配信終了日時（`actualEndTime`）・配信予定開始日時（`scheduledStartTime`）・配信予定終了日時（`scheduledEndTime`）・配信状態（`liveBroadcastContent`）を足した。
  ライブでない動画は時刻が null、配信状態は API の値のまま（通常の動画は `none`）。API の呼び出し・ユニットは変えていない
- **変化の判定の扱い**: 足した4項目を `LATE_KEYS` とし、`changed_keys()` は**保存済みの行にその項目が無ければ比べない**。ただし
  `--mode new` の配信予定・配信中の枠の取り直し（`plan_new()`）だけは `backfill=True` で比べる
  - 選んだ理由: (1) verify でそのまま比べると、足す前の全行（14,096本）が「値が変わった」になり、上限200本で止まる（下の実データでの確認）。
    (2) 比べる対象から完全に外すと、今ある配信予定の枠（41本）に予定の時刻が入らず、カレンダーに要る値が次に何か変わるまで入らない。
    (3) 項目を一度持った行は通常どおり比べるので、配信予定の時刻の変更は拾える
  - 代わりの案として「verify で1回だけ `--allow-many-changes` を付けて全件を追記する」も考えたが、層1が1回で約14,000行（数十MB）増え、
    足した項目は放送済みの動画には今回の用途で要らない（載せるのは今日以降）ので採らなかった。過去分を埋めるときに別に決める

  `test_headers_cover_all_saved_fields`）なので、`HEADERS` に4項目を足した。位置は「状態」と「概要欄」の間（既存の列の位置は概要欄以外変わらない。概要欄は 11列目→15列目）

  ほかの項目が変われば追記して足した項目も入る、保存済みの値の変化は比べる、配信予定の枠は new で埋めて以後は冪等、上限を超える数の足す前の行でも何も追記しない）、
