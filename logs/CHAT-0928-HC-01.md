  `calendar.google.com` を通さない。2026-09-21 の DJ-01 では通っていた。環境が変わった）。WebFetch も同じく遮断。
  Calendar API（`www.googleapis.com`）は通るが、認証なしでは「unregistered callers」で 403。鍵はセッションに無い

  （YouTube の題名「第43期鳳凰戦~A１リーグ第９節Ｃ卓~」とはタイトル戦名の有無・表記が違う）

  `events.list`（公開カレンダーは共有なしで読める見込み。未確認）。(3) 環境の Network access に `calendar.google.com` を足してセッションから読む（平野さんの設定）

### Calendar API の添付・サムネイル（前提の確認）

`developers.google.com` はこのセッションから遮断されていたため、同じ内容を持つ API の discovery 文書
（`https://www.googleapis.com/discovery/v1/apis/calendar/v3/rest`、revision 20260826）の Event の説明で確かめた:

- Event に画像・サムネイルの項目は無い（`image`・`thumb`・`photo`・`icon` を含む項目名は0）
- `attachments`: 「File attachments for the event」。変更には `supportsAttachments=true` が要り、1件に最大25個。
  `fileUrl` は「Google Drive のファイルを添付するときは Drive API の Files の alternateLink の形で」。`iconLink` は「custom third-party attachments のときだけ変更できる」
- `gadget`: 非推奨（誕生日カレンダーのメタデータを返すためだけに残る）
- `source`（url・title）: 予定の作成元の URL。**作成者にしか見えない**ので、公開カレンダーの閲覧者向けには使えない
- `description`: HTML を含められる
- **前提のとおり、任意の画像をサムネイルとして出す手段は API に無い。** 添付は Drive のファイルが基本（「Drive に限る」と明言する文は discovery 文書には無い。公式のリファレンスのページは読めなかった）

### 手順3(c): 設計案

**A. 何を1件にするか（決定: 配信の枠ごとに1件、ライブだけ）**

- YouTube の枠1本 = 予定1件。公開版とメンバー限定版で2件になる。直近2か月で 178件（1か月約90件）
- 予定表から作る「先の予定」は、YouTube に枠が出るまでは予定表の1予定（1対局）につき1件の仮の予定にし、枠が出たらそれに置き換える（下の D）
- 対象: チャンネルのライブ全部（Focus M・女流勉強会・開幕式などを含む）か、放送対局（タイトル戦・リーグ戦）に限るか → 判断が必要

**B. 表の形（3層のスプレッドシートに足す案。チャット側の「機械が書く表」と「平野さんが書く表」を分ける案を基にする）**

| タブ | 書く人 | 行 | 列 |
|---|---|---|---|
| 【4】予定表（機械） | 機械（毎日全件置き換え） | 予定表の予定（今日以降、放送対局と見分けたもの）1件1行 | 予定表のUID・日付・件名・説明（抜粋）・結び付いた動画ID（機械の推定、公開版/限定版）・取得日時 |
| 【5】配信予定（平野さん） | 平野さん（機械は末尾に追記だけ） | 予定表のUID 1件1行（【3】と同じ「機械が新しい行を足し、平野さんが埋める」形） | 予定表のUID・開始予定・終了予定・動画ID（公開版）・動画ID（限定版）・載せる（Y/N）・備考・追加日 |

- 【3】と同じく、平野さんの表は機械が毎日書き直さない（書くと消える問題が無い）。結び付けは UID で、行の並びに依らない
- 別案: 平野さんの表だけにし（UID・日付・件名も機械が追記した値をそのまま残す）、【4】を作らない。タブは1つで済むが、予定表の変更（日付の移動・取り消し）を機械が上書きできない。
  予定表は連盟が後から直すことがありうるので、**機械の表を分ける案を推す**
- 別案2: スプレッドシートを使わず、リポジトリにファイル（`data/…jsonl`）を置いて平野さんがブラウザで編集。/live の運用と揃わないので推さない

**C. 結び付け**

- 公開版と限定版: 公開版の概要欄の「メンバーシップ限定放送ページ」の URL で対にする（無い枠は単独）
- 予定表の予定 ↔ YouTube の枠: 同じ日（日本時間）で、題名から【2】と同じ抽出（`live_extract.war_of()`・`analyze()` のタイトル戦・期・ステージ・卓）が一致するものを機械が【4】に推定として書き、
  平野さんが【5】の動画IDで確定・訂正する（空なら推定を使う、【3】の補正と同じ規則。`-` で「結び付けない」）
- 予定表の件名の書き方が読めていないので、抽出が効くかは予定表を読んでから確かめる

**D. 重複させない識別（カレンダーの予定のキー）**

- 既存と同じく私的拡張プロパティ: `ryoei=live` と、`video=<動画ID>`（枠が出た後）または `yotei=<予定表のUID>`（枠が出る前）
- 枠が出たら、`yotei=` の仮の予定を**更新**して `video=` を付ける（削除して作り直さない。閲覧者の通知・リンクを保つ）。限定版の枠は新しく作る
- 予定IDの指定（base32hex）は使わない（削除後の衝突。#379 と同じ理由）

**E. 時刻の優先順位（案）**

| | 1番 | 2番 | 3番 | 4番 |
|---|---|---|---|---|
| 開始 | 実際の開始（`actualStartTime`） | YouTube の予定の開始（`scheduledStartTime`） | 【5】の開始予定（平野さん） | 予定表の時刻（あれば） |
| 終了 | 実際の終了（`actualEndTime`。無ければ開始＋長さ） | 【5】の終了予定 | YouTube の予定の終了（`scheduledEndTime`） | 開始＋既定の長さ（タイトル戦・種類ごとの仮置き。例: 半荘の卓 2時間） |

- 平野さんの入力を YouTube の予定の開始より下に置くか上に置くかは判断が必要（YouTube の予定は連盟の設定値で、平野さんの値は予定表・告知から読んだ値）
- 実際の時刻での上書き（「配信の翌日以降」）は、毎朝の取り込みの `--mode new` が放送済みの枠を取り直した翌朝に自然に起きる

**F. 説明文**

```
対局者: A、B、C、D
実況: E / 解説: F
配信: https://www.youtube.com/watch?v=<ID>（メンバー限定）
メンバー限定版: https://www.youtube.com/watch?v=<ID>   ← 公開版の予定にだけ
サムネイル: https://i.ytimg.com/vi/<ID>/hqdefault.jpg  ← 下の G の案
```

- 選手・実況・解説は層1の概要欄に `extract_players_and_staff()` をかけ、【3】に補正があれば補正を優先。「？？？？」のような未定の値は出さない
- 限定の有無は層1の「限定」。題名に【メンバー限定】があるので件名にも自然に出る
- 件名: YouTube の題名そのまま（例「第43期鳳凰戦~A１リーグ第９節Ｃ卓~」）か、整えた形（例「鳳凰戦 A1 第9節C卓【限定】」）か → 判断が必要
- 枠が出る前の仮の予定は予定表の件名＋「（配信枠未定）」など

**G. サムネイル**

- 予定の見た目のサムネイルにする手段は無い（上の確認）。代わりの案:
  1. **説明文にサムネイル画像の URL（または配信 URL のみ）を載せる**（推す。費用・権限が増えない。Google カレンダーの表示で画像が埋め込まれるかは未確認で、リンクになる見込み）
  2. サムネイルを Google ドライブに置いて添付にする。Drive の書き込みスコープ・置き場（共有ドライブ等）・一般公開の共有が要り、表示は添付のファイルのチップで、サムネイルとしては出ない見込み。推さない
  3. 載せない

**H. 実行の契機**

- 毎朝の `update-live-channel.yml`（02:43 JST）の層1の取り込み（配信予定の枠の取り直しを含む）の後に、カレンダーの同期のジョブを続ける案を推す（同じ日の層1で書ける）。
  シートへの書き込み（`LIVE_SHEETS_SA_KEY`）とカレンダー（`GCP_SA_KEY`）で認証が違うので、ジョブを分ける
- 予定表の読み取り（【4】の書き直し・【5】への追記）も同じワークフローの1ジョブにする
- 1日1回だと、当日に作られた枠・当日の時刻変更は翌朝まで出ない。放送日に合わせて昼にもう1回動かすかは判断が必要（YouTube API は1回あたり数ユニット）
- 書き込みの安全策は既存に倣う: 手動実行の既定は dry-run、1回の削除が上限を超えたら止める、手で足した予定（`ryoei=live` が無い予定）には触らない
- 過去の分（ライブ 4,091本）をさかのぼって載せるかは判断が必要（載せるなら初回の書き込みは誕生日と同程度の15分前後）

**I. 層1の取り込みに足すもの（実装するとき）**

- `build_record()` に `scheduledStartTime`・`scheduledEndTime`・`actualEndTime`（と、要れば `liveBroadcastContent`）を足す。API 呼び出しは今のままで、ユニットは増えない
- 足すと `--mode verify` の変化の判定で全ライブが「変わった」になる（上の注意）。【1】の列も増える（`write_live_layer1.py`）
- サムネイルは動画IDから決まる URL で足りるので、層1に保存しない案を推す
