### 手順1: 原因

**結論: 前提（G 列の値のクリア）とは違い、原因は AF-11 のコードの変更（12a3516f）。** 帰り道の生成は「プロ」シートを `generate_jpml_pros.QUERY` で読み、
列の**位置（添字）**で X ID・note ID を取っている。12a3516f でその QUERY から G・H を外したため、I 以降の位置が2つずつ前にずれた。

- `scripts/lib/wayhome.py` の `index_player_links(pro_rows, interviewees)`: 選手名（添字 `PRO_NAME_INDEX = 0`）で行を引き、
  1件だけ一致した行の `PRO_X_ID_INDEX = 8` を X ID、`PRO_NOTE_ID_INDEX = 10` を note ID にする。龍龍ID を鍵にしたり、龍龍ID が空の行を飛ばしたりはしていない
- 呼び出し元: `generate_wayhome_episodes.py`（個別38ページ）と `generate_video_wayhome.py`（一覧 `video_wayhome.html` のヒーロー）。
  どちらも `fetch_sheet(jpml_pros.SPREADSHEET_ID, jpml_pros.SHEET_NAME, jpml_pros.QUERY)` の結果を渡す
- `jpml_pros.QUERY` の変化（12a3516f、AF-11、03:50 UTC にcloudflareへ）:
  - 前: `SELECT A,B,C,D,E,F,G,H,I,J,K,…` → 添字8 = I（X ID）、10 = K（note ID）
  - 後: `SELECT A,B,C,D,E,F,I,J,K,L,M,…` → 添字8 = K（note ID）、10 = M（YouTube のチャンネルID）
- 表に出るのが遅れた理由: AF-11 のマージの再生成（8bd7573b）は `regenerate.py --changed` が `generate_jpml_pros.py` → `jpml_pros` だけを選んだ
  （`pages_for_changes()` は `scripts/generate_<page>.py` と `<page>.js` しか見ず、ほかのスクリプトからの import を追わない）。
  HC-09 のマージ（`scripts/lib/` を含む）で全ページの再生成になった a64c4915（06:15 UTC）で、はじめて帰り道が作り直された
- **「消えた」だけでなく、誤ったリンクも出ている。** a64c4915 の前後で、39ファイル（個別38＋`video_wayhome.html`）の見出しの横のリンクを比べた:

  | 変化 | ファイル数 |
  | --- | --- |
  | X のリンクが消え、何も出なくなった（K・M が空） | 17 |
  | X のリンクが消え、note のアイコンが YouTube のチャンネルID（`note.com/UC…`）を指す | 7 |
  | X のリンクが note ID を指し（X ID と note ID が同じ4ファイルは結果的に正しい）、note のリンクが消えた | 11 |
  | X のリンクが note ID を指し（2ファイルは結果的に正しい）、note のアイコンが YouTube のチャンネルID を指す | 4 |

  39ファイルすべてが変わった。ほかに `sitemap-wayhome.xml` の lastmod 38件・`sitemap-pages.xml` 1件が変わった
- 「プロ」シートの今の値（gviz、生成と同じ経路、07:2x UTC）: 在籍（Y 列 = Y）1,100行で、G・H の非空 0（クリア済み）、I（X ID）非空 856、K（note ID）非空 204。X ID は残っている
- 検証（G 列のクリアでは説明できないこと）: 今のシートを旧 QUERY（G・H を含む）で読むと、G・H は空でも列は返り、添字は保たれる（列数26）。
  その行で `index_player_links()` を通した X・note のリンクは、a64c4915 の前の39ファイルと **39/39 一致**した。新 QUERY（列数24）では上の表のとおりずれる。
  → **値のクリアだけなら帰り道は変わらなかった**。変えたのはクエリの列の除外
- 本番: `https://ryoei.pro/wayhome/76OsWTSSnso.html` の HTML を curl で取得し、a64c4915 の後と同じ誤ったリンク（X が note ID、note が UC…）であることを確かめた（HTML の確認で、ブラウザでの見え方ではない）

### 手順3: 直し方の案（決定ではない）

- **案1（推奨）: 帰り道に自前のクエリを持たせる。** `lib/wayhome.py` に `PRO_QUERY = 'SELECT A,I,K WHERE Y = "Y"'`（名前・X ID・note ID）を置き、添字を 0・1・2 にする。
  2本の生成は `jpml_pros.QUERY` の代わりにこれで読む（`generate_live_pages.py` などの `SELECT A,I,J` と同じ形。`jpml_pros.QUERY` が今後変わっても影響しない）。
  テストで「PRO_QUERY の列記号と添字の対応（A→名前・I→X ID・K→note ID）」を固定する（`test_jpml_pros.py` の QUERY の読み方と同じ手）
  - 変わるファイル: `scripts/lib/wayhome.py`・`scripts/generate_wayhome_episodes.py`・`scripts/generate_video_wayhome.py`・`scripts/tests/`（帰り道のテスト）
  - 再生成で変わる範囲: 帰り道の39ファイルが a64c4915 の前に戻る（今のシートで模擬して 39/39 一致）。`sitemap-wayhome.xml` の lastmod。
    `scripts/lib/` の変更なのでマージの再生成は全ページになる（他のページは差分なしの見込み）
- 案2（最小）: `PRO_X_ID_INDEX = 6`・`PRO_NOTE_ID_INDEX = 8` に直す。2行で済むが、`jpml_pros.QUERY` を借りて位置で読む形が残り、次に QUERY を変えると同じことが起きる
- 案3（戻す）: 12a3516f の QUERY の変更だけを戻すのは不可（`generate_jpml_pros.py` の行のアンパックも同時に変わっているため、jpml_pros.html が壊れる）
- **急ぎで戻す方法（シート側）: 無い。** 原因が値ではなくクエリなので、「プロ」G 列を版の履歴から戻しても帰り道は変わらない（龍龍への依存が戻るだけ）
- 反映の経路: 本番に出すには再生成が要る。今は GitHub Actions がジョブを始めない（支払い・使用上限）ため、push 契機の再生成も毎朝の再生成も動かない。
  Billing が直るまで待つか、セッションで `python3 scripts/regenerate.py video_wayhome wayhome_episodes` を実行して生成物もコミットするか（通常は Actions がする再生成を手で行う形になる）は平野さんの判断
- どちらで直すか: 触るファイルは AF・HC・CW のどの未マージのブランチとも重ならず、どちらのチャットでも衝突はしない。
  原因は AF-11 の変更だが、AF の龍龍の廃止は締めくくりの段階（AF-14・15 は Actions の支払いで中断中）で、帰り道のコードは AF の作業範囲の外。
  一方で原因の調べはこの HC で済んでいる。**HC（または独立の指示）で案1を行い、AF には「AF-05 の洗い出しに帰り道が抜けていた」ことを申し送る**のがよいと考える
- 再発防止の候補（別件）: `regenerate.py --changed` が import 先を追わないため、共有する定数（`jpml_pros.QUERY` 等）の変更で依存ページが作り直されず、ずれが後から出る。
  案1で「QUERY を借りる所」が無くなれば、今回の型は起きなくなる
