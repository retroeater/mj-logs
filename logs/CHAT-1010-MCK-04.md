### 手順2: 投稿からシートの行を作る対応（案）

| 列 | 投稿のどの値から | 自動で作れるか |
|---|---|---|
| A 名前 | 投稿者（`author_id` → アカウント → 名前の対応表） | 作れる |
| B X URL | `https://x.com/<アカウント>/status/<id>` | 作れる |
| C 画像 | 添付の写真（`expansions=attachments.media_keys`・`media.fields=url`）の `url` を `?format=jpg&name=240x240` の形に直す | 作れる（写真のある投稿のみ） |
| D 日付 | `created_at` を JST の日付に | 作れる（既存の行と99%同じ規則） |
| E 店名・F メニュー・G 駅・H カテゴリ | 本文 | **人の判断が要る**（本文から候補を出すことはできるが、決めるのは平野さん） |
| I タグ | G・H から | G・H が決まれば作れる（既存の行の規則。数式なら貼らない） |
| J 店URL | 本文の `entities.urls` の展開先が Google マップなら | 投稿に地図のリンクが入っているかは**未確認**（試し取りで確かめる） |
| K 表示 | — | 既定 `Y`。外すかは人の判断 |

お店の投稿の見分け方の候補（試し取りで当たり外れを数える）:

1. **写真の有無**: 既存の行の 99.6% に C（写真）がある。写真の無い投稿は外す
2. **返信・リポストを外す**: タイムラインの `exclude=retweets,replies`
3. **本文の地図のリンク**: `entities.urls` の展開先が `maps.app.goo.gl`・`goo.gl/maps`・`google.com/maps`。J の 96% が地図の URL なので、投稿にも入っていれば強い手がかり
4. **本文の決まった形**: 店名・メニューの書き方、ハッシュタグ、位置情報（`geo`）の有無。既存の行の投稿を読んで規則を探す（下の「既存の行の投稿で確かめる」）
5. **日に何件**: 既存の行は1日に0〜数件。同じ日の写真付きの投稿が多い日は、お店以外が混じる手がかり

**既存の行の投稿で確かめる方法**: シートの B から投稿 ID を1人10件（2025年11〜12月の行から）選び、`GET /2/tweets?ids=…`（1回で100件まで）で本文・添付・`entities`・`geo`・`author_id` を取る。全件が「お店の投稿」だと分かっている投稿なので、上の候補3・4がどれだけ当たるか（取りこぼし）を数えられる。`author_id` も返るので、user lookup（1件 $0.010）を呼ばずに `GET /2/users/{id}/tweets` に要る ID が分かる。逆に「お店以外の投稿を拾ってしまうか」は、次のタイムラインの試し取りで、既存の行がある期間の投稿のうち行の無いものを数えて見る

### 手順3: 試し取りの動かし方（案）

読んだ規則: CLAUDE.md「ブランチ運用」の `.github/workflows/` の行、docs/notes/github-actions.md「ワークフローを変更したとき」（docs/notes/branch-operations.md の同じ節は移した先への参照）。新しいワークフローは既定ブランチに無いと作業ブランチで手動実行できない（404）ので、**副作用の無い既定（dry-run）でマージしてから `cloudflare` で手動実行する**。ワークフローを足したら docs/notes/github-actions.md「ワークフローの一覧」の表に行を足す（`scripts/tests/test_workflows_table.py`）。

#### 案A（おすすめ）: 試し用のワークフローを新しく作る

- `.github/workflows/x-timeline-trial.yml`（`workflow_dispatch` だけ。schedule は持たず、Worker の予定表〈`workers/scheduler/schedule.json`〉にも入れない）と `scripts/x_timeline_trial.py`・テスト
- 入力: `mode`（`ids`＝既存の行の投稿 ID を読む／`timeline`＝期間のタイムラインを読む）、`handles`、`start_time`・`end_time`、`dry_run`（既定 `true`。呼ぶ予定の件数と見込みの費用だけを出す）
- **件数の上限はスクリプトの定数**（入力では上げられない）: 1回の実行で読む投稿 250件まで（$0.005×250＝**$1.25 が上限**）、`timeline` は1人1ページ（100件）まで。user lookup は呼ばない（`author_id` を使う）
- 1回目の内容（見込み）:
  - `ids`: 1人10件×2人＝20件（$0.10）
  - `timeline`: 1人100件×2人＝200件（$1.00）。期間は `start_time=2025-11-15`・`end_time=2026-01-07`（既存の行がある期間と重ねる）。返ってきた100件がどれだけの日数にわたるかで投稿の頻度（1日何件）が分かり、未反映の期間（谷岡 2025-12〜・平野 2026-01〜、今日まで約10か月）の全件の件数と費用を見積もれる。直近 3,200件を超えて古い期間が取れなければ、空で返る（それ自体が「頻度が高く全件は取れない」の答えになる）
  - 合計 220件・**約 $1.10**（同じ投稿を UTC の同じ日に読み直しても二重には請求されない、前提のとおり）
- **出力の置き場所**: Actions の成果物（`actions/upload-artifact`、保持 3日）に JSON（投稿 ID・投稿日時・写真の有無・`entities.urls` の展開先のホスト・ハッシュタグ・本文）。リポジトリは private で、成果物は mj-logs に写らない（mj-logs に写るのは実行の一覧の `actions/status.md` だけ）。ジョブのログとサマリには件数と規則の当たり数だけを出し、本文は出さない。Code は次の指示で成果物を読んで集計し、ログには件数・規則だけを書く
- 失敗の扱いは `collect_saikyo_images.py` の分類（401・402・クレジット切れ・429）をそのまま使い、そのときは以降を呼ばずに終える
- **XAP の処理と重ならない時刻**: X API を呼ぶのは毎日 04:10（`update-sns-book.yml`、Worker から。user lookup を1回30件まで、$0.30/日まで）だけ。試し取りは手動実行なので、**04:00〜04:40 を避けて昼間に1回**動かす。呼ぶエンドポイントが違う（user lookup と投稿の読み取り）ので、レート制限の枠は分かれる見込み（未確認）。クレジットは共有なので、実行の前に平野さんが X の開発者画面で残高を見る
- 費用の上限を超えない仕組み: 上の定数に加え、`dry_run=true` の実行で予定件数を確かめてから `false` で1回

#### 案B: 既存の `update-sns-book.yml` に入力を足す

- `mode` に試し取りを足せば Secret・失敗の扱いを共有できるが、毎日の更新のワークフローを変えることになり、壊すと毎日の更新に響く。呼ぶ側（Worker の `scheduled`）の振る舞いも確かめ直しになる
- **おすすめしない**（試しのために本番の毎日の処理を触るため）

#### 平野さん自身の分を自分の投稿の料金（$0.001）で取れるか

- 前提のとおり、安い料金はアプリの持ち主のユーザーの認証（ユーザーのアクセストークン）で取るときだけ。今の Secret `X_BEARER_TOKEN` はアプリの認証（Bearer）なので、案Aのままでは平野さんの分も $0.005 で数えられる見込み
- 確かめ方: (1) アプリ「ryoei.pro」の持ち主が平野さんの X アカウントかを開発者画面で見る（平野さん）。(2) 試し取りの後に開発者画面の使用量で、平野さんの分の100件にいくら付いたかを見る。(3) 安い料金を使うには、平野さんのアカウントでユーザーのアクセストークンを作り、別の Secret に入れる（新しい鍵が増える）
- 差額の見込み: 平野さんの分が全件で数百件なら $0.005 と $0.001 の差は数ドル以内。試し取りの段では Bearer のままでよい、が Code の提案
