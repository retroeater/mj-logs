### 手順3: 設定案

**Log が使えない代わりの様子見**: 最初は「人なら通れる」Managed Challenge を、高めの閾値で入れる。Pro のチャレンジ系は上限を超えたリクエストだけが対象になる（Duration なし）ので、人が巻き込まれても一瞬で済む。Security Events で当たった相手を数日見て、誤検知が無ければ閾値を下げる。これを Log モードの代わりにする。

#### 案1（先に入れる）: HTML の連続取得に Managed Challenge

| 項目 | 値 |
|---|---|
| Rule name | `Throttle rapid HTML fetches (#124)` |
| 条件式（Edit expression） | `(ends_with(http.request.uri.path, ".html") or ends_with(http.request.uri.path, "/")) and not cf.client.bot and not starts_with(http.request.uri.path, "/cdn-cgi/")` |
| With the same characteristics | IP |
| When rate exceeds | 1段目 **60 requests / 1 minute**（数日様子を見て誤検知が無ければ 2段目 30 / 1 minute） |
| Then take action | Managed Challenge |
| Duration | 選べない（Pro のチャレンジ系は上限を超えたリクエストだけにかかる） |
| Cache status | 変えない（Pro では外せない） |

- 誤検知の見込み: 人はページを移るたびに HTML を1件取るだけなので、1分に60件（1秒1件を1分続ける）には届かない。当たるのは、検証済みでないクローラやスクレイパーが /live・title/ などを続けて取る場合（推測）
- 効き目の限界: カウンタはデータセンターごとで、IP を替えながら取る相手には効かない

#### 案2（必要になったら2本目に）: すべてのリクエストの大量取得を Block

| 項目 | 値 |
|---|---|
| Rule name | `Block bulk fetches (#124)` |
| 条件式 | `not cf.client.bot and not starts_with(http.request.uri.path, "/cdn-cgi/")` |
| With the same characteristics | IP |
| When rate exceeds | **300 requests / 1 minute** |
| Then take action | Block（応答は既定の 429） |
| Duration | 10 minutes |

- 誤検知の見込み: キャッシュが空のときの読み込みでも1ページ6〜20件程度なので、1分に15ページ以上を連続で開かないと届かない。平野さんが開発者ツールでキャッシュを切って確認を続けると近づきうる（推測）
- 位置づけ: 「ボット系の設定は1つずつ変える」ため、**案1と同時には入れない**。案1の後、画像・JS まで大量に取る相手が Events や Traffic に見えたときに検討する

#### 入れた後の確かめ方

1. 入れた直後: セッションから `curl -sS -o /dev/null -w '%{http_code}\n' https://ryoei.pro/` など数件が 200 のままであること（Claude Code に頼める）
2. 数日後: Security → Analytics → Events を Service「Rate limiting rules」で絞り、当たった相手の ASN・User agent・Path を見る。AS15169（Google）・AS8075（Microsoft）・AS714（Apple）が無いこと
3. 月次: #304 (8) の Search Console のクロールの統計情報で 403 が増えていないこと
4. 任意: 効くことを確かめたいときは、セッションから短時間に `.html` を70件取り、途中から 403（`cf-mitigated: challenge`）になるかを見る（セッションの出口 IP が1分ほどチャレンジされる。平野さんの許可を得てから行う）
