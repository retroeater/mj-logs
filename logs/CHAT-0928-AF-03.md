### 手順3: 原因の候補・影響・直し方の案

**原因の候補**（断定できない）

1. **龍龍側（またはその前段の WAF・ファイアウォール）が、GitHub Actions のランナーの接続元（Azure の IP 帯）からの接続を、時々まとめて落としている。** 接続の段階で30秒応答が無い（拒否ではなく無応答）ので、パケットを捨てる型の遮断と合う。
   同じ日の別の時刻には届いており、常時の遮断ではない。ランナーは実行ごとに接続元が変わるため、「その接続元が過去に大量に取りに行ったか」で決まる回数制限か、特定の IP 帯を一時的に落とす仕組みが考えられる
2. **龍龍のサーバーのその時間帯の不調。** #9 は日曜 22:00 UTC（月曜 07:00 JST）ごろ、#8 は日曜 01:54 UTC（10:54 JST）で、時間帯はそろっていない。このセッションから今つながることとは矛盾しないが、裏づけも無い
- 「844件を取りに行ったこと自体が引き金」の見立て（#8 の RN-03）は、#9 では当たらない: #9 は1件目から失敗しており、この実行が大量に取りに行く前に届いていない。
  ただし同じ日の 21:03 UTC に `check-image-links.yml`（`jpml_pros.html` の龍龍の画像も HEAD で確かめる）が走っており、その接続元と #9 の接続元の関係は分からない
- `URLError` の reason（タイムアウトか、名前解決か、接続拒否か）はスクリプトが捨てているため、ログからは切り分けられない

**影響**

- 龍龍側で写真が差し替わったことの週1の検知が止まる（サイトの写真は古いまま表示され続けるが、リンク切れではないので `check-image-links.yml` では拾えない）
- #424 が閉じず、本文が 09-21 の誤検知（修正済み）のまま残る。平野さんから見ると「差異がある」ように見え続ける
- ページ・シート・デプロイへの影響は無い（確認だけのワークフロー）
- 失敗の通知（実行の失敗のメール）が週1で来る可能性。自動で追いつく仕組みは無く、次の定期実行（10-04 日曜 19:00 UTC 予定）が届けば、そこで #424 が更新・クローズされる

**直し方の案**（決定ではない）

- 案A: **中断したら時間をおいてやり直す**
  - 変更箇所: `scripts/check_ron2_images.py`（1件目から連続で失敗したときは、例えば10分待って最初からやり直す、を2回まで）。あわせて失敗の記録に `URLError` の reason を残す（原因の切り分け用）。`timeout-minutes: 40` は、やり直しの分だけ延ばす
  - 副作用: 失敗の日は最長で1時間ほどランナーを使う。同じランナー（同じ接続元）からのやり直しなので、接続元ごとの遮断なら効かない
- 案B: **ジョブをやり直す（接続元を変える）**
  - 変更箇所: `check-ron2-images.yml`。中断したら、別の schedule（例えば数時間後の2本目の cron）か、`workflow_run` で別ジョブとして再実行する。スクリプトは変えない
  - 副作用: ワークフローが複雑になる。ランナーが変わっても同じ IP 帯なら効かない。やり直しの回ぶん龍龍への負荷が増える
- 案C: **中断しても issue に「中断した」ことを書く（検知の結果の見え方だけ直す）**
  - 変更箇所: `check_ron2_images.py` で中断時も途中までの result.json（`aborted` の印つき）を書き、ワークフローの「結果をissueに反映」を `if: always()` にして、#424 に「中断（龍龍に届かず）」と書く。ジョブは失敗のまま
  - 副作用: 遮断そのものは直らない。issue の本文が「中断」で上書きされ、前回の差異の一覧が見えなくなる（残す書き方にするなら手間が増える）
- 案A と案C は組み合わせられる。いずれもワークフローまたはスクリプトの変更なので、docs/notes/branch-operations.md「ワークフローを変更したとき」の手順（作業ブランチでの手動実行）が要る。
  手動実行そのものが龍龍への844件のアクセスになるため、確かめは `--limit` 相当を使う形にするのがよい
- 変えない案: 次の定期実行（10-04）を待つ。#9 と #8 以外の定期実行は成功しているので、一時的なものなら何もしなくても戻る。#424 は届いた回に閉じる
