### 3. 統一の仕方の候補（コードは変えていない）

今の仕組み: 店の店名は「店名を持つ最も新しい投稿」の値（`scripts/generate_log_pages.py` の `group_shops()`、`SHOP_FIELDS`）。投稿の店名が店の店名と違えば、`search_data()` が投稿の6要素目に入れ、`assets/log.js` の結果の投稿の行（`mj-log-post-meta`、:397）に出す。検索は `prepare()`（:41-70）が店の店名と投稿の店名をすべて `shop.names` に入れ、店名の候補と検索欄の語の突き合わせに使う（「HARBS」で「ハーブス」の店が当たる）。

- (A) 平野さんが【3】の「店名」の列を投稿 ID ごとに直す
  - 手間: 123セル（88店）。要確認の 10店は、別に place_id の列（または店名に並べた複数の店）を直す 26件の判断が要る
  - コードは変えない。直した後の次の log/ の再生成で、店の店名・投稿の行・候補がそろう
  - 後で増える揺れには効かない。変換（`convert_x_posts.py`）が新しい投稿の本文から店名を取るので、同じ店でも投稿の書き方で表記が変わる（今の95店も同じ経路で生じた）。揺れが出るたびに【3】を直す運用になる。また、最も新しい投稿が店の店名になるので、新しい投稿1件の表記で店の店名が変わる（例: 2番の店は今「ルードメール」1件が店名で、「ルー・ド・メール」2件は投稿の行に別名で出る）
- (B) 生成のときに、店ごとの表記を一つにそろえる
  - 直すファイルと関数の見込み: `scripts/generate_log_pages.py` の `group_shops()`（店の店名を「最も新しい投稿」から「投稿の数が最も多い表記 → 同数なら最も新しい」に替える。この調べの案と同じ決め方）と `search_data()`（投稿の6要素目を出さない、または別名の一覧として店の側に持つ）、`assets/log.js` の `prepare()`（別名を店の側から読む）と結果の投稿の行（:397、別名を出さない）。テストは `scripts/tests/test_log_pages.py`・`scripts/tests/js/log.test.js`、文書は docs/notes/log-page.md の「データの持ち方」「結果」
  - 検索への影響: 投稿の行に別名を出さなくするだけなら、`prepare()` が投稿の6要素目から別名を集めているため、別名（「HARBS」「サイゼリヤ」など）では当たらなくなる。別名でも当てたままにするなら、search.json に店ごとの別名の一覧（12要素目など）を足し、`prepare()` がそれを `shop.names` に入れる形にする（候補にも別名が出続ける。候補に出したくなければ、検索欄の語の突き合わせにだけ使う）
  - 手間: コードの変更1回（上のファイル・テスト・文書）。【3】は触らない
  - 後で増える揺れへの効き方: 新しい投稿の表記が増えても、店の店名は数の多い表記に保たれ、投稿の行にも出ない（機械的・語の揺れはそれだけで吸収できる）。ただし案が誤る店（71番の「灯火」と「灯花」のような誤字、件数が同じで新しい側を採る店）は、結局【3】を直すことになる。要確認の 10店（place_id の付け違い・複数の店を並べた店名）は (B) では直らない
- (A) と (B) は両立する: (B) で揺れを吸収し、要確認の 10店と、数の多い表記が誤っている店だけを (A) で直す、という組み合わせもある
