### 3. 結論

- **確かめられたこと: HTML に ETag が無いのは、Worker の静的アセットの配信の段階で起きている。** ryoei.pro のゾーンの設定を通らない workers.dev でも、HTML にだけ付かない（ほかの種類には付く）
  - ryoei.pro のゾーンの機能（Email Obfuscation・Replace insecure JS libraries・RUM など）は、HTML の ETag が無いことの原因ではない（少なくとも唯一の原因ではない）。workers.dev は ryoei.pro のゾーンの外という前提による（公式の明記は確かめていない）
  - robots.txt は逆に、workers.dev では ETag があり ryoei.pro では無い。こちらはゾーン側（管理 robots.txt の前置）で外れている
- **CW-12 の「切る順番」の前提（ゾーンの機能を切れば ETag が戻る）は崩れた。** Email Obfuscation などを切っても HTML の ETag は戻らない見込み。ただし Email Obfuscation は #120 の記録と状態が食い違っている件として別に扱う価値はある（影響なしで切れることは CW-12 で確かめた）
- 推測（未検証）: `wrangler.jsonc` の `html_handling: "none"`（#89）または `not_found_handling: "404-page"` と、HTML の配信経路の関係。公式の headers のページ（https://developers.cloudflare.com/workers/static-assets/headers/ ）は ETag を既定で付けるとし、HTML の例外を書いていない
- 次の切り分けの案: 作業ブランチで `html_handling` を既定（`auto-trailing-slash`）に変えたプレビューを作り、workers.dev の別名 URL で HTML に ETag が付くかを見る（本番に影響しない。ただし wrangler.jsonc の変更になるので、やるかは判断が要る）
