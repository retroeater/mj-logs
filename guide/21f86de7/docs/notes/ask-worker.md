# データ・コンシェルジュの Worker（mj-ask、#542）

houou/ のトップで鳳凰戦のデータに言葉で質問できる欄。決定は `docs/decisions/houou.md`「2026-10-11（CHAT-1011-AIC-01）」。
実装は3つに分ける（grill Q13）: (1) データと検索〈済〉、(2) Worker と質問欄〈済、2026-10-11 から本番で動作〉、(3) 週次の cron〈済。ブックへの書き出しの最初の本番の実行は 2026-10-19（月）9:00 JST の見込み〉。
1日の上限は全体 200・IP ごと 10（2026-10-16。試行中の全体は 50 だった）。公開は #540。

**質問欄の置き場所（2026-11-04）**: ページの中の質問欄（houou/・ouka/・jwrc/・wrcr/・saikyo/ のトップと新トップ）はやめ、入口を共通ナビの AI 検索のアイコン1つにした
（帯のすぐ下に横断の欄を開く。`assets/nav.js`・`assets/top_ask.js`、`contest: "all"` と `context`。docs/notes/design.md「共通ナビ（新しい形）」）。
pro/ のトップの欄も pro/ の作業で外した。ページの中の欄の部品は 2026-11-04 に片付けた（`ASK_TEMPLATE`・`ASK_HEAD`・`ASK_NOTICES`・`ASK_MAX` を消し、`assets/houou_ask.css` の規則は `style.css` の「質問欄の部品」へ移した）。`assets/houou_ask.js` と `scripts/tests/test_houou_ask.py` の突き合わせ（`pickPlayers`・`splitPlayers`）の検査も 2026-11-04 に消した（3人と「ほか N名」の分け方の検査は `test_top_page.py` の `TopAskJsTest`）。
下の各大会の「X/ の質問欄は `contest: "X"` を添える」は廃止した大会別の欄の記述で、Worker は `contest` を指定した問いを今も受け付ける（外すかは #654）。

## 最強戦（saikyo/、#626。公開は #627〈2026-10-26 に閉じた〉）

- `scripts/generate_ask_data_saikyo.py`（`ask_data_saikyo`）が `workers/ask/data-saikyo.json` を書く。最強戦のページと同じ読み方・同じ集計（ランキングは `generate_saikyo_pages.py` の `build_division_rankings()`）。対象は全出場者。読み・入会期は名簿にいる在籍者だけ
- 期ではなく年度で数える大会なので、`contest.yearly` が真。`query.mjs` は term・from・to を年度（上限 9999）として読み、型 `player` は年度ごとの卓と結果（`yearlyPlayer()`）、最強戦だけの型 `year`（ある年度の対局と勝ち上がり者、`yearMatches()`）を使う。型は champions・final・player・year・ranking（`contest.types`）。リーグ・前期後期は無い（1回目の出力の形の league は null だけ）。決勝は `FINAL_MATCH_NAME` の決勝の卓
- 指示は `ask.mjs` の `SAIKYO_PLAN_SYSTEM`（部門は `SAIKYO_DIVISIONS`）と、最後に足す `saikyoLines()`（「現最強位」は決勝のある最新の年度、「今年」は対局のある最新の年度）。2回目は「日本プロ麻雀連盟の」を付けない（連盟の大会ではないため）。記録の型は「saikyo:champions」の形
- 最強戦だけ渡す結果を足す（2026-10-24、CHAT-1024-SKP-10。本番の5問で、年度で絞った最強位を「1回」、渡さなかった人数〈others〉を「ほかに2人」、3人まで渡した同率を全員と書いたため）: champions の各人に通算の回数 `total`（年度で絞っても通算）、ランキングの同率 `tie.names` は10人まで渡し、超えた人数を `tie.others`（2026-11-02 に5大会へそろえ、`TIE_NAMES` = 10 の1つにした）。2回目の指示（`ANSWER_LINES.saikyo`）に total・others・tie.others の読み方を書く。（当時はほかの大会の同率の名前は3人のまま。2026-11-02 にそろえた）
- 選手の成績（player）には、部門ごとの通算の値 `totals`（`data-saikyo.json` の `totals`。`generate_ask_data_saikyo.py` の `totals_data()` が個人成績の部門別のタブと同じ値で書く。規定に届かない勝率は入れない）を添える。`count` は卓の行の数（対局数）なので、2回目の指示で「出場の回数ではない。回数は totals を書く」とする（2026-10-25、CHAT-1025-SKP-11。「出場は36回」と答えたため）
- 部門は6部門（2026-10-27）。外した予選優勝・予選決勝・予選通過は `SAIKYO_REMOVED`（外した部門 → 近い部門）に持ち、1回目の指示でその部門を近い部門に読み替え、2回目の指示（`ANSWER_LINES.saikyo`）で答えの頭に「その部門はありません。」と書かせる。旧い名前の「通過率」は勝率、「出場」は出場数に読み替える（指示の言い換え）
- 出典の名前は、歴代最強位（champions）が「麻雀最強戦 歴代最強位」、決勝（final）が「麻雀最強戦<年度> 決勝結果」。player の結果は個人成績と同じ（ファイナルの決勝の通過は「最強位」、ほかの決勝の通過は「優勝」）
- 新しいトップの質問欄（段1 は仮の URL `/saikyo/next/`）が `contest: "saikyo"` を添える。Worker の変更はマージで本番に入るが、この問いを送るのは noindex の仮のトップだけ（公開まで辿れない）。work/ ブランチのプレビューからは `/api/ask` に届かない（`ALLOWED_ORIGIN` が本番のため）ので、本番の質問欄での試しは公開の前の指示で行う
- テストは `workers/ask/test/saikyo.test.mjs`

## データ（data.json）

- 決勝（鳳凰位）: `title/search.json`（`generate_title_pages.py` の生成物）の鳳凰戦の期。**鳳凰位を獲った期はここを正にする。**

## Worker（mj-ask）

`ryoei.pro/api/*` のルートで動く別の Worker（grill Q4）。サイトの Worker `mj`（静的アセット）は変えない。ルートは同じホスト名の Custom Domain より優先される
（公式の Routes のページ）。`/api/` は 2026-10-11 の時点で使われておらず（`/api/ask`・`/api/` とも 404、`_redirects`・`_headers` に行なし）、
Rate limiting rules の条件（`.html` か `/` で終わるパス）にも当たらない。

POST `/api/ask`（本文 `{"question": "…"}`）の流れ:

1. `Origin` が `ALLOWED_ORIGIN`（`https://ryoei.pro`）でなければ 403。Secret・D1・上限の設定が無ければ 503（`unavailable`）
2. 空・200字（`QUESTION_MAX`、コードポイントで数える）を超える問いは 400（`invalid`）。数えない
3. 回数（grill Q7）: JST の暦日を鍵に、全体（`daily_counts`）と IP（`ip_counts`。IP は「Secret の塩・日付・IP」の SHA-256 だけ）を読み、上限なら 429（`limit`、`scope` は `daily` か `ip`、`resetAt` は翌0時 JST）。
   受け付けるときに両方を `INSERT … ON CONFLICT DO UPDATE … RETURNING n` で1つ足し、前日以前の `ip_counts` を消す（1回の batch）。同時に来て上限を越えたら 429
4. Claude（`claude-haiku-5-5`）の1回目: structured outputs（`output_config.format` の JSON schema `PLAN_SCHEMA`）で `{type, assumedTerm, args}` を返させる。型は query.mjs の6つ（鳳凰戦は `entry` を足した7つ）と `none`。鳳凰戦の指示の最後に、「現在」「今」をデータのある最新の期（`latestPeriod()`）で読ませる一文（`currentLine()`）と、「現在の鳳凰位」「現鳳凰位」などを決勝のある最新の期（決勝のデータの最大の期）の `champions` で読ませ、リーグの読み方より先に当てる一文を足す（`hououLines()`。2026-10-19。「現在」を第43期と読んで決勝の無い期の鳳凰位を引き、「答えられません。」になったため、#618）。女流桜花は一文なしで「現女流桜花は？」に答えられた（2026-10-19 の本番）ので足していない（確定、2026-10-20）。鳳凰戦の一文に「現タイトルホルダー」も入れた（確定、2026-10-20）。直す前は「現在の鳳凰位は？」を league 型の第43期前期の「鳳凰位」（リーグの名前）として引いていた（D1 の `questions` の id 201: `{"term":43,"half":"前","league":"鳳凰位"}`、unanswered）。WRC リーグの指示の最後には、「現タイトルホルダー」「今のチャンピオン」などを最新の決勝の期の `champions`（from・to にその期）で読ませる一文（`holderLine()`）を足す（2026-10-19。`PLAN_LINES`）
5. `none`、または `runQuery` が見つからない・名前が決まらない・引数が不正なら「答えられません。」（候補があれば添える）。2回目は呼ばない。

- 2回目を要る大会が1つなら、その大会の欄と同じ2回目（言語の混ざり・内部の言葉の作り直しは1回。大会が5つでも上限より1回多くまで）。2つ以上なら1回にまとめる（structured outputs で大会の id ごとの欄に答えを書かせ、指示には大会ごとの読み方〈`ANSWER_LINES`〉を並べる。言語の混ざり・内部の言葉が残った大会だけを1回まとめ直す〈作り直しの呼び出しが失敗したら1回目の答え。空の欄・頼んでいない大会の欄は写さない〉。「리그」「league」の置き換えは `tidyAnswer()`）。まとめた答えの欄が空の大会は落とす
- 1つの大会の1回目が失敗したら、その大会を落として残りで答える（Workers Logs に「横断の1つの大会で失敗」）
- 答えた（候補を挙げたを含む）大会だけを並べる。どの大会でも答えられなければ、ほかの大会の案内があればそれを、無ければ先頭の大会の答え（「…のどれにも見つかりません。」など）を返す
- 費用の見込み（2026-11-03、送る文字数で比べた）: 1つの大会の欄は1問あたり約 $0.0004（2026-10-19 の実績）。横断で5大会を並べる問いは送る文字数が約4倍（1回目の指示と型の定義が大会ごとに要る）で、約 $0.0016 の見込み。選手名の問い（記録のある大会が2〜3）は約2〜3倍

記録（`questions`）: 1問1行。`context` の大会だけで答えたときも型は `all:<大会>:<型>`（大会別の要求の行と分け、大会別の要求を消す時機を記録で見るため）。型は `all:<大会>:<型>` を答えた大会の順に `,` でつなぐ（例 `all:houou:player,jwrc:player,saikyo:player`。答えられなかったときは返した1つの大会〈案内のある大会、無ければ答えの文のある先頭の大会〉、Claude の失敗のときは選んだ大会すべて）。引数は大会の id ごとの引数の JSON（`{"houou":{…},"jwrc":{…}}`）。
週次の書き出しの見出しは変えていない（型の列に入る）。

## HTTP 403 の調べ（2026-10-26、CHAT-1026-AIC-08）

2026-10-19〜25 に「失敗: Claude plan: HTTP 403」が4回（`jwrc:`・`wrcr:`・`ouka:`）。同じ問いはほかの時刻では答えている。

- 公式の API のエラーの文書（platform.claude.com の errors）では 403 は `permission_error`（キーの権限）。キーの権限・ワークスペースの上限（上限は 400）なら毎回落ちるはずで、4回だけなのと合わない
- 公式の Supported regions に、日本・韓国・台湾・シンガポールはあり、香港・中国本土・マカオ・ロシアは無い。Workers は既定で「リクエストを受けたところに最も近いデータセンター」で動く（Cloudflare の Placement の文書）。外への `fetch` もそこから出るので、対応していない地域に近い利用者の問いは、対応していない地域から Anthropic を呼ぶことになる。4回だけ・時刻がばらばらなのと合う（仮説。記録からは確かめていない）
- 2026-10-26 から、失敗の記録に応答の本文と request-id、拠点（colo・国）を書く（上の「Worker」の8）。次に起きたら D1 の `answer` で分けられる
- 直す案（入れていない。本番の動きと費用に関わるので平野さんの判断）: `wrangler.jsonc` に `placement`（Smart Placement、または対応地域のクラウドの region を指す Placement Hints）を足し、Anthropic を呼ぶ Worker を利用者の近くでなく対応地域で動かす
- 見てほしい所: Cloudflare のダッシュボードの `mj-ask` の Observability（失敗の時刻の `答えの作成に失敗: …` の行と、要求の colo・国）、Anthropic の Console の Logs（その時刻の 403 の行と理由）
- 結果（2026-11-02）: 2026-10-21 23:54 JST の失敗は拠点 HKG・国 HK（平野さんが Observability で確認）。2026-11-01 02:32 JST の2回は記録の答えが「失敗: Claude plan: HTTP 403 forbidden Request not allowed（拠点 HKG・HK）」で、`error.type` は `forbidden`（文書のキーの権限の `permission_error` と違う）。配置は変えず（対応地域の外の利用者に制限を迂回して提供することになるため）、`forbidden` を地域の制限と見て理由の分かる文を返す（上の「Worker」の8）。見たのは1つの国の2回だけなので、ほかの理由で `forbidden` が返ると分かったら `message` や国で絞る（`ask.mjs` の `簡略化:`）

## 週次の cron（実装3、grill Q9）

`wrangler.jsonc` の `triggers.crons` に `0 18 * * 1`（UTC の日曜 18:00 = **月曜 3:00 JST**。ほかの定期実行〈月次 2:00・週次 3:00・日次 4:00 JST〉にそろえた。2026-11-02 までは `0 0 * * 2`〈月曜 9:00 JST〉。初回は 2026-11-09〈月〉3:00 JST）。
区切りの「今週の月曜 0 時（JST）」は 3:00 に動いても同じ月曜 0 時になるので、日曜 23:59 JST までの行が入り、月曜 0:00〜3:00 の行は次の回に入る（欠けも重なりも無い。`weekly.test.mjs` で確かめる）。**Cloudflare の Cron Triggers の曜日は 1 = 日曜・2 = 月曜**（公式の Cron Triggers のページ「Days of the week go from 1 = Sunday to 7 = Saturday」。ほかの cron の 0 = 日曜と違う）。
2026-10-11〜13 は誤って `0 0 * * 1`（日曜 9:00 JST）になっていた（CHAT-1013-AIC-05 で直した）。Cron Triggers はアカウントで 250 本まで（Workers Paid。2026-10-21 までの Free は5本）で、`mj-scheduler`（毎分）と合わせて2本。
入口は `index.mjs` の `scheduled`、本体は `src/weekly.mjs`。

1. **ブックへの書き出し**（`GOOGLE_SA_KEY` と `ASK_SHEET_ID` があるとき）: 専用のブックの最初のシートに、1行目の見出し（日時・質問文・結果・型・答え・引数。空のブックなら最初に足し、行があれば毎回書き直す〈4列だったブックを6列にする、2026-10-19〉）に続けて、
   D1 の `questions` のうち「ブックの最後の行の日時より後」かつ「今週の月曜 0 時（JST）より前」かつ「90日以内」の行を日時の順に足す（`values:append`、`valueInputOption=RAW` で質問文を式として扱わせない）。
   前の週の行が足され、取りこぼした週があれば次の回に拾い、同じ回が2度動いても同じ行を二度足さない。結果は「答えた」「答えられなかった」「候補を出した」「ほかの大会を案内した」「地域で使えない」、型・答え・引数が無ければ空
2. **ブックの90日を過ぎた行の削除**: 2行目から日時の古い順に並んでいる前提で、先頭から続く90日より前の行を消す（`batchUpdate` の `deleteDimension`）。ブックの行を手で並べ替えると、古い行が残ることがある
3. **D1 の90日を過ぎた行の削除**: `DELETE FROM questions WHERE asked_at < <90日前>`。鍵が無いときや Google の呼び出しが失敗したときも行う
4. 鍵かブックの ID が無ければ、Workers Logs に「週次: 鍵(GOOGLE_SA_KEY)かブックの ID(ASK_SHEET_ID)が無いため、ブックへの書き出しを飛ばす」と書き、1・2 を飛ばして正常に終わる。最後に `週次: {cutoff, until, sheet, d1Deleted}` の1行を書く

Google の認証: サービスアカウントの JSON の鍵の `client_email`・`private_key` で JWT を RS256（WebCrypto）で署名し、`https://oauth2.googleapis.com/token` でアクセストークンに替える（スコープ `https://www.googleapis.com/auth/spreadsheets`。読み書きできるのは共有されたブックだけ）。

1. Workers & Pages → `mj-ask` → Settings → **Runtime variables and secrets**（B4 と同じ画面）→ **Add**
2. Type **Secret**、Variable name **`GOOGLE_SA_KEY`**、Value に C1 の4の JSON ファイルの中身を全部（メモ帳で開いて Ctrl+A → Ctrl+C）→ **Deploy**
3. ダウンロードした JSON を PC から消す（ごみ箱も空にする）
4. ブックの ID（C2 の4）をチャットに伝える。ID は秘密の値ではないので、指示で `wrangler.jsonc` の `ASK_SHEET_ID` に書く（ダッシュボードで変数を足しても、次のデプロイで `wrangler.jsonc` の値に上書きされるため）
5. 最初の書き出しは、`ASK_SHEET_ID` を入れた後の月曜（当時は 9:00 JST、2026-11-09 から 3:00 JST）。Workers Logs の `週次:` の行と、ブックの行で確かめる

## キーの差し替え（期限の前・漏れたとき）

1. Claude Console → Settings → API keys → Create key で、同じ条件（ワークスペース `ryoei-pro-ask`・本人・1年。1年を超える期限は作れなかった）の新しいキーを作る。今のキーの期限は 2027-10-11 0:00 JST、差し替えの予定は 2027-09-28
2. `mj-ask` → Settings → Runtime variables and secrets → `ANTHROPIC_API_KEY` の値を新しいキーに替えて **Deploy**
3. houou/ のトップから1問送って答えが返ることを確かめる
4. Console の API keys で古いキーを消す（漏れたときは 2 の前に消す。その間は質問欄が「いまは答えられません。」になる）
5. 次の期限の予定をカレンダーに入れ直す

`IP_HASH_SALT` を替えると、その日の IP ごとの数がいったん0に戻る（全体の数は戻らない）。
