# 誕生日カレンダーの同期（#379）

名簿の誕生日を「誕生日」Google カレンダーへ、GitHub Actions から Google Calendar API で同期する。
方式の比較は `docs/logs/CHAT-0919-BD-01.md`、実装の経緯は `docs/logs/CHAT-0919-BD-03.md`。

## 仕組み

- 一覧: `scripts/lib/birthdays.py`。名簿（`lib/meibo.py`）と「プロ」シート（表示 Y）を登録名で結合し、誕生日が空欄の人を除く。#393・#286 でも使う
- 同期: `scripts/sync_birthday_calendar.py`
  - 1人1件の毎年繰り返す終日予定。タイトル「<登録名>」、説明欄は X のリンク（無い人は空）。
    カレンダー名が「mj_誕生日」で、月表示が「誕生日」だらけになるため、タイトルに「誕生日」を付けない（平野さんの決定、2026-09-20）
  - 繰り返しの開始日は「実行日（日本時間）の18年前以前で直近のうるう年」の各人の誕生日（2026-09-20 時点で 2008年）。
    麻雀プロは全員満18歳以上なので、生まれる前の年に誕生日を出さないため（2000年起点だと出る人がいた。2026-09-20）。
    うるう年なので 02/29 も作れる。開始年は4年ごとに変わり、変わった後の初回の同期で全件が「更新」になる
  - 02/29 生まれは `RRULE:FREQ=YEARLY;BYMONTH=2;BYMONTHDAY=-1`（2月の最終日。平年は 02/28）。
    初回の書き込み後、小車祥・佐藤あいりが 2027年2月は 2/28、2028年2月は 2/29 に出ることを平野さんが確認した（2026-09-19）。
    公式文書では、誕生日専用の予定の種類の説明（guides/event-types）に 02/29 の誕生日へこの規則を使うよう書かれている
  - 誕生日専用の予定の種類（eventType "birthday"）は使わない。公開範囲が「非公開」固定で、説明欄・拡張プロパティを持てないため（2026-09-20、CHAT-0919-BD-05 のログ「手順3」）
  - この同期が作った予定は私的拡張プロパティ `ryoei=birthday` と `name=<登録名>` で見分け、登録名をキーに追加・更新・削除する。
    手で足した予定（プロパティが無いもの）には触らない
  - 名簿・「プロ」を2回読み、結果が変わる・人数が 1,000〜1,200 を外れるときは止める。1回の削除が30件を超えるときも止める（`--allow-many-deletes` で解除）
- ワークフロー: `.github/workflows/sync-birthday-calendar.yml`。手動実行の既定は「カレンダーを読んで差分を出すだけ」。週次の実行は「週1の同期」節
- 認証: アプリケーションのデフォルト認証情報（ADC）。ワークフローの「Google に認証」の手順（`google-github-actions/auth`）だけが鍵を扱う
- 使う値:

| 種類 | 名前 | 中身 |
|---|---|---|
| Secret | `GCP_SA_KEY` | サービスアカウントの鍵（JSON ファイルの中身そのまま） |
| 変数（Variables） | `BIRTHDAY_CALENDAR_ID` | 「誕生日」カレンダーのカレンダーID（公開カレンダーの ID のため Secret にしない） |

キーを予定IDでなく拡張プロパティにした理由: 予定IDは削除後も `cancelled` として残るため、登録名から決まる ID だと、
退会した人が再入会したときなどに同じ ID の作成が衝突し、復元の処理が要る。拡張プロパティなら毎回新しい予定を作ればよく、
`privateExtendedProperty` でこの同期の予定だけを一覧できる。

## 設定手順（平野さん、Windows のブラウザで。1〜8 は 2026-09-20 に完了）

### 1. Google Cloud プロジェクトを作る

1. ブラウザで https://console.cloud.google.com/ を開き、`ryoei.net` のアカウントでログインする
2. 画面上部のプロジェクト選択 →「新しいプロジェクト」→ 名前（例: `ryoei-pro`）を入れて「作成」
3. 作ったプロジェクトが上部で選ばれていることを確かめる

### 2. Calendar API を有効にする

1. 左上のメニュー →「API とサービス」→「ライブラリ」
2. 「Google Calendar API」を検索して開き、「有効にする」

### 3. サービスアカウントを作り、鍵を発行する

1. 「IAM と管理」→「サービス アカウント」→「サービス アカウントを作成」
2. 名前（例: `birthday-calendar`）を入れて「作成して続行」。ロールは付けずに「完了」（カレンダーの権限は手順5で与える）
3. 一覧に出たサービスアカウントのメールアドレス（`birthday-calendar@<プロジェクトID>.iam.gserviceaccount.com`）を控える
4. そのサービスアカウントを開き、「鍵」タブ →「鍵を追加」→「新しい鍵を作成」→「JSON」→「作成」。JSON ファイルがダウンロードされる
   - 「鍵の作成が組織のポリシーで無効」と出たら、ここで止めて Claude Code に伝える（Workload Identity Federation に切り替える。ワークフローの「Google に認証」の手順だけを変える）
5. ダウンロードした JSON は手順4で登録したら PC から削除する（ごみ箱も空にする）

### 4. 鍵を GitHub の Secret に登録する

1. https://github.com/retroeater/mj/settings/secrets/actions を開く
2. 「New repository secret」→ Name に `GCP_SA_KEY`、Secret に JSON ファイルの中身を全部貼る（メモ帳で開いて Ctrl+A → Ctrl+C）→「Add secret」

### 5. 「誕生日」カレンダーを作り、公開し、サービスアカウントに共有する

1. https://calendar.google.com/ を開く（`ryoei.net` のアカウント）
2. 左の「他のカレンダー」の「＋」→「新しいカレンダーを作成」→ 名前「誕生日」（実際には「mj_誕生日」にした）→「カレンダーを作成」
3. 左の一覧の「誕生日」にカーソルを合わせ「︙」→「設定と共有」
4. 「アクセス権限」で「一般公開して誰でも利用できるようにする」にチェック（範囲は「すべての予定の詳細」）
   - Workspace の管理設定で外部への公開が制限されていると、この項目が選べないことがある。その場合は Claude Code に伝える
5. 共有の前に、管理コンソールで予備カレンダーの外部共有を緩める。サービスアカウント（`…gserviceaccount.com`）は
   組織外の扱いになるため、既定のままでは次の手順で「予定の詳細の表示」までしか選べない（2026-09-20）。
   https://admin.google.com/ →「アプリ」→「Google Workspace」→「カレンダー」→「共有設定」で、
   「予備カレンダーの外部共有オプション」を「すべての情報を共有する（外部ユーザーにカレンダーの変更を許可する）」にする
   - 「メイン カレンダーの外部共有オプション」は変えない（2026-09-20 は「空き時間情報のみ」のまま）
6. 「特定のユーザーまたはグループと共有する」→「ユーザーやグループを追加」→ 手順3で控えたサービスアカウントのメールアドレス、
   権限は「予定の変更」→「送信」
7. 同じ画面の「招待状の自動承諾」を「招待状を表示しない」にする。
   第三者の招待でこの公開カレンダーに予定が紛れ込まないようにするため（2026-09-20）
8. 同じ画面の「カレンダーの統合」にある「カレンダー ID」を控える（`c_…@group.calendar.google.com` の形）

### 6. カレンダーIDを GitHub の変数に登録する

1. https://github.com/retroeater/mj/settings/variables/actions を開く
2. 「New repository variable」→ Name に `BIRTHDAY_CALENDAR_ID`、Value に手順5で控えたカレンダーIDを貼る →「Add variable」

### 7. 手動実行する

ワークフローは `cloudflare` にマージされてから実行できる（既定ブランチに無いワークフローは起動できない）。

1. https://github.com/retroeater/mj/actions/workflows/sync-birthday-calendar.yml を開く
2. 「Run workflow」→ チェックを外したまま（apply なし）で実行 → 実行結果の Summary に
   「この同期の予定 0件を読んだ」「追加 1,073件前後 / 更新 0件 / 削除 0件」と出ることを確かめる（読み取りと認証の確認）
3. もう一度「Run workflow」→「カレンダーに書き込む」にチェックを入れて実行（約1,070件の書き込みに約15分かかる。2026-09-19 の初回は 14分34秒）
4. Google カレンダーで「誕生日」を表示し、次を確かめる
   - 誰かの誕生日の日に「<登録名>」が出る。説明欄に X のリンクがある
   - 02/29 生まれの2名（小車祥・佐藤あいり）が、2028年（うるう年）は 2/29、2027年（平年）は 2/28 に出る
   - 開始年（2026-09-20 時点で 2008年）より前の年には出ない
5. apply なしでもう一度実行し、「追加 0件 / 更新 0件 / 削除 0件」になる（冪等）ことを確かめる

### 8. タイトル・開始日の変更を反映する（2026-09-20 に実施済み。CHAT-0919-BD-05・BD-06 のマージ後に1回）

既存の予定は、タイトル（「<登録名> 誕生日」→「<登録名>」）と開始年（2000→2008）の違いで「更新」になる。更新は予定を置き換える（PUT）。

1. 「Run workflow」→「カレンダーに書き込む」にチェックを入れて実行 → Summary が「追加 0件 / 更新 1,073件前後 / 削除 0件」であることを確かめる
   （書き込みに約15分かかる。追加・削除が 0件でなければ、書き込む前の同じ実行の Summary を Claude Code に伝える）
2. チェックを外して（apply なし）もう一度実行 → 「追加 0件 / 更新 0件 / 削除 0件」になることを確かめる
   - **ここで「追加 1,073件前後」と出たら、置き換えで同期のキー（拡張プロパティ）が消えている。** 以後 apply ありで実行せず（重複して全件が追加される）、Claude Code に伝える
3. カレンダーで、タイトルが「<登録名>」になり、2008年より前の年に出ないことを確かめる

結果（2026-09-20）: apply ありで「追加 0 / 更新 1,073 / 削除 0」（14分27秒）、apply なしで全部 0件。
カレンダーでタイトルが登録名だけになり、2008年1月から出て 2007年2月には出ないことを確認した。

## 週1の同期（2026-09-20 に有効にした）

`.github/workflows/sync-birthday-calendar.yml` の `schedule` で毎週月曜 05:17 JST（日曜 20:17 UTC）に実行する。初回は 2026-09-21。

`check-meibo.yml`（05:07）の10分後に置いたのは、名簿と「プロ」シートの不一致がその朝のうちにissue（#370）へ出ているようにするため。
誕生日の一覧は両者を登録名で結合するので、件数の異常や削除の原因をそのissueと突き合わせられる。

- schedule の実行は書き込みまで行う（`APPLY` が `github.event_name == 'schedule'` で真になる）。手動実行の既定は dry-run のまま
- 削除の上限（30件）は schedule でも外れない（`inputs.allow_many_deletes` が schedule では空になる）。
  1回の削除が30件を超える週は書き込まずに止まる。Summary の「削除」の一覧を見て正しければ、手動実行で
  「削除が上限を超えても続ける」にチェックを入れて実行する
- 定常の週は冪等（追加・更新・削除がすべて0件）で書き込みが無く、短く終わる。開始年が変わる年（4年ごと）は全件が「更新」になり約15分かかる
- 失敗に気づく方法は GitHub からの通知（Actions の失敗のメール）。通知の設定はブラウザでしか確かめられないため、
  届かないときは https://github.com/settings/notifications の Actions の項目を見る。成功した週は通知されないので、
  結果を見るには https://github.com/retroeater/mj/actions/workflows/sync-birthday-calendar.yml を開く
