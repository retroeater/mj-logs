# チャット側の定型作業（レビュー・振り返り・申送り）と場面ごとの手順

チャット側（claude.ai）向け。平野さんが「レビュー」「振り返り」「申送り」と言ったときに行う手順と、`docs/notes/chat-side-operations.md`「場面ごとに読む文書」の表から開く場面限定の手順（2026-10-14 に chat-side-operations.md から移した、#492）。
受け手側（Claude Code）の規則は CLAUDE.md、チャット側の日常の規則は `docs/notes/chat-side-operations.md`。この文書には容量の上限を置かない。

## レビュー

### 何をするか

プロジェクトの指示・プロジェクトのメモリー・容量制限のある文書（CLAUDE.md・docs/handover.md・docs/notes/chat-side-operations.md・docs/instruction-template.md）を
包括的に見直し（妥当性・重複・冗長・不整合）、サイズを削減する。人間向けの可読性は下がってよく、Claude チャット／Code として問題がなければ表現等を圧縮してよい。
メモリーはチャット側が直接直し、文書は Claude Code 向けの指示文（判断待ちで止め、整理後の全文をログに貼らせて読み比べ → マージの指示）で行う（2026-09-29、平野さんの決定）。

### 観点のチェックリスト

- (a) 古い事実: 「最終更新」の日付、期日を過ぎた行、閉じた issue、仕組みの変更で変わった記述
  - handover 5章の表の issue は REST か Code で Open/Closed を確かめ、閉じたものの行を直す
  - プロジェクトのメモリーの「docs/decisions に書かれるまでの控え」は、docs/decisions・docs/notes に書かれたものを消す
- (b) 文書間の重複: 規則の本文はどれか1つを正にし、ほかは参照にする
- (c) 冗長: 括弧内の事例・経緯は `docs/notes/handover-archive-2026.md` へ、場面限定の手順は `docs/notes/` へ
- (d) 消してはならないもの: 規則そのもの、issue 番号、止まる条件、決定の内容

指示文に書くこと:

- 文書ごとの前のサイズと目安、候補の一覧
- 対応表（候補 → 確かめた事実 → 処理）を経過に書かせる
- 整理後の全文をログに貼らせ、判断待ちで止める
- 足す行を指示するときは、archive の「外した記録」（`handover-archive-2026.md` の「〜から外した記述」の節）を先に確かめる（前に意図して外した行を足し戻さないため）

### 成果物の形

- メモリーの直し（チャット側が行う）
- 文書: 指示文 → 整理後の全文の読み比べ → マージの指示

## 振り返り

### 何をするか

そのセッション（チャット）の会話を全部読み返し、不明点・不整合・別の提案がないかを確認して報告する（日付不明、平野さんの決定）。

### 観点のチェックリスト

- 指示文の書き方で往復が増えた点
- Claude Code の報告と実物の食い違い
- 平野さんの手作業で詰まった点
- 文書・メモリーに残っていない決定
- issue の有無・状態・クローズは、検索か実物（Chrome・Code）で確かめてから書く。ログの記述は「ログにこう書いてある」と分ける
- 前回の振り返り・レビューで立てた約束（「次からこうする」）が守られたか。守られなかったなら、約束のほうが過剰でなかったか

### 成果物の形

チャットでの報告。「うまくいかなかったこと」「事実として残る点」「提案」に分けて書く。

報告の後、必ず Fable 5.1 のレビュー（advisor）を入れる。平野さんがモデルを Fable 5.1 に切り替え（`/model claude-fable-5-1`）、Fable 5.1 が報告を読み直してレビューを返す。チャット側はモデルを切り替えられないので、報告の末尾で切り替えを促す（2026-10-11、平野さんの決定）。

## 申送り

### 何をするか

- **平野さんが「申送り」と言ったら**、振り返りの知見のうち**機械的に確かめられる手順（仕組み・検査・issue）に落とせるものだけ**を
  issue や資料に書き残す指示文を作る（抽象的な心得は書かない）。**追記先の残り容量を測らせ、規則だけを書かせる**（事例は archive へ）

### 観点のチェックリスト

- **知見ごとに、計算的センサー（テスト・hook・ワークフロー）→ 推論的センサー（Code の着手前の確認手順など、受け手が手順で確かめるもの）→ ガイド文 の順に検討する。** 落とせないもの（抽象的な心得）は書かない。ガイド文を選んだときは、指示文に「知見 → 選んだ層 → 理由」の表を入れる（無いと Code は止まる、#492）
- 追記先の残り容量（容量制限のある文書なら上限・警告域との差）
- 規則と理由の一句だけか（事例は archive へ）
- **規約が守られないときは、内容ではなく書き方を疑うこと。** 手順の1つとして並べた規約より、他の作業との順序
  （「〜より先に行う最初の手順」）で書いた規約のほうが守られる（CLAUDE.md「作業ログ」節の着手時の push。chat-side-operations.md から移した）

### 成果物の形

issue や資料に書き残す Claude Code 向けの指示文。

## 指示の種類ごとの確かめ

`docs/notes/chat-side-operations.md`「書く前に実物で確かめる」の規則に加えて、指示の種類ごとに次も確かめる。

- 最初の指示: 関係する issue の本文・コメント、未マージの work/ ブランチ、既存の仕組み（テストの置き場所など）が「ある」こと
- マージ・クローズの指示: issue の Open/Closed と比較（`/compare/cloudflare...<ブランチ>`）。別のチャットが並行して進めていることがある
- 複数の指示にまたがる作業: 最初の指示で、論点に関係する issue（クローズ済みを含む）を洗い出させる。検索語には変える対象そのものの語を入れる
- 起票・方針の提案、運用ルールや文書整理: 同じ論点の issue を、クローズ済みとコメントの決定まで含めて確かめる（#328）。読めなければ提案せず、確かめさせる指示にする。
  仕組み（検査・自動化）の issue を起票する指示では、直近3セッションのログでページ・内容の変更があったかを Code に数えさせて目的欄に書かせる（仕組みづくりを続けるかは平野さんが数を見て決める、#492）
- インフラやデプロイの提案: 実物の設定（CLAUDE.md「構成」、`docs/notes/cloudflare.md`）
- 他のセッションが同じ日に変えている領域（`title/` など）や前の指示から写す前提: 使う直前に確かめ直させる（写すときは対象ファイルの範囲が同じかも）。**「残っている作業」を書く前に、docs/decisions/ の置き換え・済の注記と、コード・シートに今もあるかを確かめる**（または手順に入れる）。
  **複数のチャットが同じ仕組みを変えているときは、見込みを平野さんに伝える前と指示を書く前に、もう一方のチャットの最新のログを読む**（触るかを推測で言わない。`git branch -r --no-merged origin/cloudflare` の各ブランチと cloudflare の差に変えるファイルがあるか、変える関数・定数の呼び出し元〈別のページの生成を含む〉、ページが凍結中・`regenerate.py` の `FROZEN_FROM_ALL` でないかを見る。調べの指示〈起票・洗い出し〉にはこの3点を手順に書く）
- 一覧の行の形（表・面の行・検索の結果）を決める指示: 前提に端の実データ（いちばん長い名前・順位や日付が空・結果の種類ごと〈例: 通過・敗退・優勝・未対局〉）を書き、確かめの欄でその行を報告させる。
  平野さんにプレビューを頼む前に、チャット側が端のデータの画面を見る（端のデータで見つかる直しは1本の指示で済むため）
- 平野さんがシート（タブ）を用意した・直したと言ったとき: `docs/notes/static-generation.md`「生成を止める条件の設計」の末尾の手順に従う（生成と同じ経路で読ませてから指示を書く）

## 期日とカレンダー

- **issue に期日を書かせたら、同時にカレンダー「ryoei.pro」に予定を作る。** 件名は「【R#番号】…」、説明の冒頭に issue のリンク、色は指定しない。
  番号の無い予定も同じ。個人の予定表には書かない（コネクタは ryoei.pro だけを共有した別アカウント）
- **期日を過ぎた繰り返しの予定は、その回を済むまで翌日へ繰り越す**（別の予定は作らない）。繰越しは開いた時にまとめてよい
- **予定が済んだら・issue のクローズを知ったら、消さずに件名の冒頭に【済】を付けてグラファイトにする。** 説明欄の残課題は行き先の予定へ移す
- **動きを変える指示では、通知先の常設 issue（種類: 常設）の本文も文書更新の対象に入れる**

## 外部サービスの設定を頼むとき

- **最初の調査の指示に「権限・共有・組織ポリシーの制約」の洗い出しを入れ、実装の指示では要る Secret・変数・共有をすべて列挙する**
- **外部の API を使う実装の指示では、本番の手順の前に「そのアカウント・プランで対象の API を1件だけ呼んで通る」ことを手動実行で確かめる手順を最初に置く**
- **設定の変更を頼むときは、選択肢の意味と、ダッシュボードの画面の名前（ボタン・欄）とその影響を公式ドキュメントで確かめてから頼む**（名前から推測しない。「害は無い」と確かめずに言わない）。
  **設定が保存されたかは、スクリーンショットではなく動き（check-run・実行の結果など）で確かめる**
- **検索を止めうる変更は、疑いが出た時点で確かめる。後日に回さない**

## ほかのセッションへの共有

- **宛先は相手の「チャット」にする。** 相手のチャットが自分の Chat-Ref の指示文に書き直してから Claude Code に渡す（直接渡すと作業ログが残らない）
- Actions の失敗通知を受けたら: `docs/notes/github-actions.md`「チャット側」
- **「ログにこう書いてある」「平野さんの申告（Code が確かめるまで未確認）」「確かめた事実」を分けて書く**
- 共有文を受け取ったら、先に自分がその系列のチャット（履歴・プロジェクトの指示がある）かを確かめ、違えば平野さんに伝えてから進める
