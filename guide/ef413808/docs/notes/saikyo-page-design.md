## 2. 変換ルール

- K が「Y」の行をすべて対象にする。A が空欄でも除外しない
- 年度スラグは B の末尾4桁（`2026` → `2026`。「麻雀最強戦2026」形式でも同じ）
- 対局のまとまりは、A があれば **B + A + C**、空欄なら **B + C**
  - A が空欄のまとまりの中で ステージ + 卓 が重複した場合（同じ卓が
    離れて2回現れる、または5人以上いる）は、別々の対局が混ざった疑いとして
    年度・対局名・ステージ・卓をビルド時に警告する（生成は止めない）
  - A を後から埋めれば、次回の再生成で自動的に日付つきの対局に変わる。
    コードに年度や対局名は持たない（例外: 年度プルダウンの選択肢とページのタイトルに付ける
    大会名「麻雀最強戦」は、生成スクリプトの定数 `EVENT_NAME` として持つ。SK-18。
    トップの最強位を決める対局名「ファイナルトーナメント」は、定数 `FINAL_MATCH_NAME` として持つ。#355）
- ステージの表示順は **シートの出現順の逆順**。シートは決勝→ベスト8の順に
  並んでいるため、表示は ベスト8 → 決勝 になる。
  ステージ名から順序を導く処理は書かない（新しいステージ名が増えても
  対応不要にするため）
- 卓は E の昇順（A卓 → B卓）。E が空欄または「-」のステージは見出しを
  ステージ名のみ（例「決勝」）にする
- 卓内の並びは F の昇順（左が1位）。F が空欄の行はシート順で後ろに置く
- **通過・敗退の判定は G で行う。F では判定しない**（決勝は2位でも敗退のため）
- 優勝者は「D が決勝 かつ G が通過」の行として導出する。バッジは「優勝」
- 卓の4人全員の G が空欄 → 未対局として扱い、バッジを出さない。
  一部だけ空欄 → データ不整合としてビルド時に警告を出す
- 画像: J が `abs.twimg.com/sticky/default_profile_images/` で始まる場合、
  または J が空欄の場合は `img/avatar.svg` を使う
- リンク: 選手から連盟の選手ページ（`jpml_pros`）へのリンクは張らない。
  I が空でなければ写真全体（カード）を `https://x.com/<I>` へのリンクにする
  （`rel="noopener"`、SK-09）。I が空欄（`#N/A` 等の数式エラーを含む）なら
  カードをリンクにしない
- 名前・対局名の表記ゆれは表示側で補正しない。シート側で直す

### `/saikyo/` の配信（トップを返す）

- **`_redirects` の `/saikyo  /saikyo/  301` と `/saikyo/  /saikyo/index.html  200`**（CHAT-0918-RK-09）。
  `/title` と同じ形にそろえてある。移動先の年度を手で直す運用は無くなった
  - 2026-09-18 まではトップが無く、`/saikyo/`・`/saikyo` とも最新年度のページへ302で移動していた（SK-24・SK-26）。
    302 にしていたのは、301 はブラウザにキャッシュが残り年度の切り替え後も古い年度へ飛び続けるため
- `_redirects` は先に一致した行が効く。先頭行 `/  /index.html  200` は `/` だけに一致し（`*` なし）、`/saikyo/` とは競合しない
- `wrangler.jsonc` の `html_handling: "none"` はディレクトリの index を自動で解決しないため、`/saikyo/` には
  `_redirects` の行が要る
- `_redirects` の各行は完全一致で、`/saikyo/` と `/saikyo` は別のパスとして扱われる（SK-26 で `/saikyo` の行を足す前は 404）
- クエリ文字列: 移動先にクエリを書かない行では、元のリクエストのクエリが移動先へ引き継がれる。
  301 でも同じで、本番の `/saikyo?player=<名前>` の応答は `location: /saikyo/?player=<名前>` だった
  （CHAT-0918-RK-09 で実測。SK-26 では wrangler 同梱の asset-worker の実装で確認していた）

### アンカー

対局名を英字化する規則は持たない（新しい対局名が出るたびに人手が要るため）。
形式は次のとおり（CHAT-0914-SK-04）。

```
<対局識別子>-s<ステージ連番>[-<卓>]
```

- 対局識別子: A があれば `YYYYMMDD`。空欄なら `<年度4桁>-n<年度内の連番>`
  （連番は A が空欄の対局に、シート出現順で 1 から振る）
- ステージ連番: その対局の中でのステージの表示順（ベスト8 が1つ目なら `s1`、
  決勝が2つ目なら `s2`）
- 卓: E から「卓」を除いた英字の小文字（「A卓」→ `a`）。
  E が「-」または空欄なら卓部分ごと省略する

例: `#20260906-s1-a` / `#20260906-s2` / `#2015-n3-s1-b`

生成後に各ページの id 重複を検査し、重複があれば警告する（生成は止めない）。
**この規則でも、同じ日に同じ構成（ステージ連番と卓）の対局が2つあれば衝突する。**
2026-09-14時点の同日5件は、片方が決勝のみ（`-s1`）、もう片方がベスト8 A/B卓
（`-s1-a` / `-s1-b`）のため衝突していない。警告が出たら規則を見直す。
A を埋めると `2015-n3-...` 形式から日付形式へ変わり、未登録側の連番も
振り直されるため、日付未登録の対局へのリンクは恒久的なURLにならない。
対局の共有URL（`?match=<対局識別子>`、SK-19、4章）も同じ対局識別子を使うため、
日付未登録の対局（`?match=2015-n3`）の共有URLは恒久的なURLにならない。
識別子が変わった後の古いURLは、該当する対局が無い値として全件表示に落ちる。

## 4. 年度ページの表示

```
[麻雀最強戦2026▼] [🔍 選手名で検索  ]   ← navbar の直下に固定（SK-18/SK-19）
  [麻雀一揆（2026年9月6日）   (共有)]   ← 日付つきの対局を日付の降順
    ベスト8 A卓
      [4人を順位順に1行]
    ベスト8 B卓
      [4人を順位順に1行]
    決勝
      [4人を順位順に1行]
  ファイナルトーナメント        ← A が空欄の対局は日付なしの見出しで、
```

    角丸はカードの `overflow: hidden` が切る

    後から変えられるよう CSS 変数 `--mj-saikyo-rank-size` のまま残す。

  - 数字の大きさはカード幅の18%（`18cqi`。名前の `13cqi` より大きい）で、下限 12px（SK-11 と同じ考え方）

    暗くしない方針（SK-06）は維持する

  ブレークポイント）で 2×2（SK-08）。縦1列にはしない。左から1位→4位という
  並びが情報を持ち、2×2 なら読み順（左上→右上→左下→右下）で保たれる。
  縦1列だと卓が3つあるページで極端に縦長になる。カードは幅に応じて正方形を保つ

  廃止した
  - ホバー時: 影を elevation 3 に強め、わずかに持ち上げて拡大する
    （`prefers-reduced-motion: reduce` では動かさない）

- `img` には `width` / `height` を付ける（CLS対策）。生成時にページあたりの画像枚数を標準出力に出す
- **読み込みの優先度**（#382、CHAT-0921-SG-10）: LCP になるのは最初に出る選手写真（CHAT-0921-SG-09 で特定）。

    `fetchpriority="high"` を付け、`loading="lazy"` は**付けない**（lazy と high は同時に指定しても lazy が勝つ）

  - `<head>` に `<link rel="preconnect" href="https://pbs.twimg.com">`。**`crossorigin` は付けない**
    （`<img>` は CORS なしで読むため、付けると別の接続になって再利用されない）
  - `/live` も `.mj-saikyo-card` を使うが `<img>` は `generate_live_pages.py` が出すので、この属性は波及しない
    （`/live` の LCP は YouTube のサムネイル）

## 5. アクセシビリティ

色だけで通過・敗退を伝えない（WCAG 1.4.1）。

- 通過・敗退は順位ラベルの色で示し、文字（`alt`）でも伝える（#412。SK-13 の名前の帯から移した）。
  色は読み上げに乗らないため、通過・敗退は `alt` で伝える。未対局は順位ラベルを出さず、
  `alt` は名前のみ（SK-18）
- `img` の `alt` は名前と結果にする（例: 「佐藤太郎（3位敗退）」「佐藤太郎（優勝）」、
  順位欄が空なら「佐藤太郎（敗退）」）。ラベルの表示が数字だけでも、`alt` は数字
  だけにしない。優勝者はラベルが「1」でも `alt` は「（優勝）」
- 未対局の場合の `alt` は名前のみ
- 写真に重ねる名前（`.mj-saikyo-name`）と順位ラベル（`.mj-saikyo-rank`）は `alt` と
  同じ内容のため `aria-hidden="true"` にし、読み上げの重複を避ける。リンクのカードは
  リンク名が「佐藤太郎（3位敗退）（新しいタブで開く）」、リンクの無いカードは画像
  「佐藤太郎（3位敗退）」として、名前と結果が1回ずつ伝わる（SK-10 で Chrome の
  アクセシビリティツリーを確認）
- 対局の共有ボタンはアイコンだけのため `aria-label="<対局名>を共有"` で名前を付ける。コピーの結果は
  `role="status"` のトーストで伝える（SK-19）
- `?match=` で絞り込んでいることは画面の文言では伝えない（SK-21）。ページのタイトルの先頭に対局名を
  入れ、ページを開いたときの読み上げとタブ・履歴の名前で分かるようにする。すべての対局へ戻るリンク（4章、RK-13）は
  状態ではなく移動先を示す文言にしている

## 7. 選手写真の更新（#333）

写真のURLは「プロ」のJ列か「連盟プロ以外」の X画像URL にある（#384 で「最強戦」シートの J 列から移した。以下の「J列」は #384 より前の記述）。
シートはXのプロフィール画像URLを直接持つ。本人がアイコンを変えると
古いURLは404になり、ページ側は代替アバター（`img/avatar.svg`）に落ちる。
2026-09-16 時点で16選手・63行が該当した。

**URLを直持ちする限り、404は増え続ける。** #333 で全件を直した後も、2026-09-16 夜〜17日未明の数時間で続けて起きた:
下石戟（CHAT-0916-SK-43）、白鳥翔（23行、SK-44）、朝倉康心（20行、SK-45）。いずれも画像IDが変わっており、本人のアイコン変更による。

- **大きさによって404になる時期がずれる。** `_400x400` だけ404で `_200x200` は200（下石戟）、またはその逆（白鳥翔、Actions から）
- **実行環境によっても結果が違う。** 同じ白鳥翔のURLが、codespace では両方404、Actions では `_200x200` だけ404、翌日の codespace では `_400x400` だけ404だった。
  朝倉康心は Actions から `_400x400` が404、codespace からは両方200。取得元ごとに古い画像のキャッシュが残っているとみられる
- 生成時の到達確認（`_400x400` への置き換えと `srcset` の有無）もこの揺らぎで結果が変わり、シートが同じでも生成物が変わる（#341 のコメント）。
  Codespaceで`_400x400`への置き換えや`srcset`が外れ、Actionsの再生成で戻ることがある（見た目は変わらない）。**本番はActionsの生成が正。**
  Codespaceで生成したときのこの種類の差分はコミットしてよく、Actionsが上書きする（handover.md 2章「データの流れ」から移した）
- 検知は週1で自動化済み（下の `collect_saikyo_images.py`）。ただし検知は発生の後で、発生自体は止まらない。自前ホストはしない（#349、2026-09-18 に平野さんが判断）

**URLは拡張子の大小も区別される。** `…/2090088060/IMG_9616_400x400.JPG` は200だが `.jpg` は404になる
（井出洋介の21行がこれで壊れた、CHAT-0916-SK-36）。サイズ表記（`_200x200` → `_400x400`）を
一括で置き換えるときも、画像IDが古いままなら404は直らない。

**生成時に全員分をハンドル（I列）から解決することはしない。**
1回の生成で276ハンドルを解決する手段は、費用・レート制限・実行時間の
どれかで見合わないため（調査はCHAT-0916-SK-34。X公式APIは User Read
$0.010/件で276件あたり約$2.76、unavatar.ioは1日25件〈APIキー登録で50件〉、
ヘッドレスChromiumでの取得は1件4〜5秒で276件なら約20分）。
壊れるのはアイコンを変えた選手だけなので、404になった行だけを直す。

### `scripts/collect_saikyo_images.py`（手動実行＋週1の検知）

写真のURLをHEADで確認し、取得できないものだけをXハンドルから
解決してCSVに出す。写真とハンドルは年度ページと同じく `load_rows()` で「プロ」「連盟プロ以外」から引く（#384）。**Xの画像は `_400x400`（src）と `_200x200`（srcsetの1x）の両方を確かめ、
どちらかが取得できなければ壊れているとみなす**（シートの表記によらない。`_400x400` だけ404で
`_200x200` は200だった例がある、CHAT-0916-SK-43）。

```
python3 scripts/collect_saikyo_images.py              # 標準出力へCSV
python3 scripts/collect_saikyo_images.py -o urls.csv  # ファイルへ
python3 scripts/collect_saikyo_images.py --limit 5    # 動作確認用
python3 scripts/collect_saikyo_images.py --json result.json  # ワークフロー用
```

- **週1の検知**: `.github/workflows/check-image-links.yml` のジョブ `saikyo` が、`jpml_pros.html` の検知と同じ
  毎週月曜 03:00 JST に `--json` で実行し、常設issue「最強戦の選手写真のリンク切れ検知結果」に
  選手名・ハンドル・行数・取得できなかったURL・解決した新しいURLを書き出す。ゼロになればコメントしてクローズする
  （CHAT-0916-SK-44、#139）。通知はissue経由のGitHubの通知で、メールを直接送る仕組みは無い。
  issueがopenのまま本文だけ更新された場合は通知が来ないことがある。動作確認は `workflow_dispatch` の入力 `saikyo_limit`

- 解決は**ヘッドレスChromiumで `https://x.com/<handle>/photo` を開いて取り出す**（`--headless=old --dump-dom`）。
  curlでは取れない（JSでしか描画されず、`/photo` 以外はCloudflareのチャレンジで403）。ログインは要らない。
  1件5秒ほどかかるが、対象は404の行だけなので許容できる。解決に失敗しても検知結果は出る（状態の列に理由が入る）。
  Chromiumの場所は `CHROME_BIN` で指定できる（未指定ならPATHとよくある場所から探す。
  GitHub Actionsの `ubuntu-latest` には Google Chrome / Chromium が同梱されている）
- **当初は unavatar.io を使っていたが、1日25件（APIキー登録で50件）の制限があり16件程度でも枠を使い切るためやめた**
  （CHAT-0916-SK-36）。外部サービスへの依存も無くなった
- アカウントが消えている・凍結されている場合はページにその旨が出るので「解決不可（アカウントなし）」として区別する
- CSVは「選手名 / 直す先 / X ID / 現在のURL / 新しいURL / 状態 / 最強戦の行数」。直す先は「プロ」（J列）か「連盟プロ以外」（X画像URL）。
  **gvizは行番号を返さないため行番号は出ない。** 直す先のタブで選手名を探して置き換える（1名につき1行）
- 配信する画像のドメインは pbs.twimg.com のまま（`#9` のCSPの対象を増やさない）

### Xのデフォルトアイコン

写真のURLが `abs.twimg.com/sticky/default_profile_images/` のとき（卵型の既定アイコン）は
本人の写真ではないので、生成時に代替アバターへ読み替える（`is_default_avatar()`）。

### 写真の解像度（srcset、#341 の案2）

J列が `_400x400` のURLのとき、同じ画像の `_200x200` を srcset の 1x、
`_400x400` を 2x として出す。カードの表示は最大228pxで、DPR1なら200pxで足りる。

- 生成時に `_200x200` の到達を確認し、取れたものだけ srcset に出す
  （`small_x_images()`。2026-09-16 は231件中230件）。取れなければ `src` の `_400x400` だけになる
- 代替アバター（SVG）には srcset を出さない
- 読み込み失敗時の `assets/saikyo.js` の処理は2段（#406、平野さんの判断 2026-09-19。年度ページとトップの両方）:
  1. 失敗したのが srcset から選ばれた URL（DPR1 の 1x `_200x200`）なら、srcset だけを外して `src`（`_400x400`）を読み直す。
     `_200x200` だけが取れない写真（2026-09-19 の浅見真紀のように、取りに行く場所で結果が違うもの。CHAT-0918-SX-11）でも写真が出る
  2. それも失敗したとき（または失敗したのが `src` と同じ URL のとき。DPR2 の 2x は `src` と同じ `_400x400`）は、
     代替アバターへ差し替える。**srcset を消してから `src` を書き換える**（srcset が残ると src より優先される）
  - `saikyo.js`（`defer`）の実行前に失敗した画像は error イベントを受けられないため、実行時に読み込み済みで壊れている画像
    （`complete` かつ `naturalWidth === 0`）を拾って同じ処理をかける（CHAT-0918-SX-13。プレビューの年度ページで取りこぼしが出た）
  - 判定は `img.currentSrc !== img.src`。headless Chromium で X の画像に 404 を返して、DPR1 の1xだけ404 → `_400x400`、
    両方404 → 代替アバター（DPR1・2）、正常は変わらないことを確かめた（CHAT-0918-SX-13）

## 8. 出場者の登録漏れの検知（#431）

年度ページは、名前から「プロ」「連盟プロ以外」を引いて写真とXのリンクを出す（#384、`load_rows()`）。
**どちらからも引けない人は代替アバターになるだけで、生成は止まらず何も知らせない。**
登録漏れに気づけるよう、同じ読み方で引けない人を週1で確かめ、常設issueに書く。

### `scripts/check_saikyo_unregistered.py`（手動実行＋週1の検知）

`generate_saikyo_pages.load_name_book()` と同じ `NameBook` を作り、「最強戦」シート（表示 Y）の名前を
`resolve()` する。引けない人を、直し方の違う2つに分けて出す。

- **登録が無い**: 「連盟プロ以外」に行を足す
- **重複などで使われない**: 行はあるが `NameBook` が捨てた（同じ名前が複数ある、「プロ」にもある、
  所属団体が想定外、など）。足すのではなく既存の行を直す。判定は `lib/names.py` の警告を名前で突き合わせて拾う

```
python3 scripts/check_saikyo_unregistered.py                  # 一覧を標準出力へ
python3 scripts/check_saikyo_unregistered.py --json result.json  # ワークフロー用
```

2026-09-21 の実行では、出場者440名のうち8名が引けなかった。**8名とも「登録が無い」のではなく、
「連盟プロ以外」に同じ名前が2行ずつあって使われない**ものだった（佐月麻理子・山田独歩・木村和幸・
水巻渉・矢島亨・辻百華・鈴木達也・高口和之）。どの組も「所属補足が `-` で X ID・X画像URL が欠けた行」と
「所属補足が空で値の入った行」の組み合わせ。

### `.github/workflows/check-saikyo-unregistered.yml`

毎週月曜 06:50 JST（03:00/04:00/05:37/06:23 の週次ジョブと重ねない）と手動実行。
常設issue「最強戦の出場者の登録漏れ」を本文ごと置き換え、0名になったらコメントして閉じる
（`check-image-links.yml` と同じ作り）。

- **新規ワークフローのため、作業ブランチからの `gh workflow run` は404になる**（既定ブランチに無い。
  `docs/notes/branch-operations.md`「ワークフローを変更したとき」）。`SCHEDULE_ENABLED: 'false'` で
  schedule も dry-run にしてあり、マージ後に `cloudflare` で手動実行して確かめてから `'true'` にする
- 手動実行の `dry_run` の既定は true（issueを作らず実行サマリに出すだけ）。
  作業ブランチから実行するときは、常設issueを上書きしないよう既定のままにする
