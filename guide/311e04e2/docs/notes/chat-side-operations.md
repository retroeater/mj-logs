# チャット側（claude.ai）の運用

チャット側が Claude for Chrome で GitHub を読むときの手順と、Claude Code へ渡す指示文を書くときの注意。
handover.md 0章・3章には要点と参照だけを置き、詳細はここに書く。
Claude Code 側が守るルール（Chat-Ref・ブランチ運用・作業ログ）は CLAUDE.md が正。

**この文書には容量の上限がある**（警告26KB／失敗28KB、`assets-check.yml` が push ごとに判定。#421）。
**足すときは新しい項目でなく既存項目への統合・置き換えで入れ、規則と必要な理由の一句だけを書く。事例（どの Chat-Ref で何が起きたか）は
`docs/notes/handover-archive-2026.md`「docs/notes/chat-side-operations.md から」へ書く**（退避先に上限は無い）。
警告が出たら上限を上げずに整理する（CLAUDE.md「CLAUDE.md / handover.md の更新ルール」）。

## Claude for Chrome の使い方（2026-09-16。PC で使うとき）

**ブラウザを使う前にこの文書を読む。**

**ブラウザは、平野さんが用意した Chrome の「Claude」プロファイル（接続名「Claude in Chrome」）で使う。平野さん自身の Chrome（プロファイル）は使わない。**

リポジトリは private のため、チャット側のサンドボックスからの `git clone` / `fetch` / `api.github.com` はすべて遮断される
（`could not read Username for 'https://github.com'`、API は 403。#211）。サンドボックスから raw URL を取得する手順も使えない。
GitHub はブラウザ経由でだけ読む。

### 1つの確認につき、ブラウザの操作は1回まで

- **1つの確認につき、ブラウザの操作は1回（タイムアウト4分）まで。** タイムアウトしたら同じ操作をやり直さず、
  下の代わりの手段に切り替える。**後で別の確認をするときは、また1回試してよい。**
  一度のタイムアウトを理由に、その会話でブラウザを使うのをやめない
- 応答しなくなる事象は一時的なもので、恒久的な故障として扱わない（navigate は通るが get_page_text / screenshot / find だけが
  4分でタイムアウトする形がある。Claude Desktop の再起動では直らないことがある）
- 待つより切り替えるほうが速い
- **タブを閉じる操作はタイムアウトしやすい。** 閉じられずに残ったタブは、平野さんが閉じてよい

### 確認対象ごとの代わりの手段

| 確認したいこと | 代わりの手段 |
| --- | --- |
| 作業ログ（`docs/logs/`） | mj-logs で読む（下の「作業ログの読み方」） |
| issue・コミット・ブランチ | Claude Code に `gh` / `git` で確認させ、ログに書かせる（例: `gh issue view <番号> --comments`） |
| 本番の見え方 | 平野さんに目で確認してもらうか、Claude Code に headless Chrome で測らせる |

Claude Code 側で確認できる範囲（本番のHTMLとブラウザでの見え方の違い）は `docs/notes/cloudflare.md`
「ビルド成否と本番の確認範囲（check-runs）」。

### 作業ログの読み方

- **ログは public の mj-logs で読む。URL は平野さんが送る「ログ（公開）」の行をそのまま使う。**
  チャット側が組み立てた URL は開けず、一度読んだ URL は古い版が返ることがある。読めない・途中の版に見えるときは、平野さんに `## 報告` 節だけを貼ってもらう
- **新しい会話の始めは、平野さんが前回の最後の「ログ（公開）」の行を送る。** ガイド文書はそのログの末尾のリンク（mj-logs の `guide/<SHA>/`）から読む
- **申告をそのまま信じない。** ログ・ブランチ・issue に実行の痕跡があるかを先に確かめる
- **ブランチ名は最終報告の「ブランチ:」の行か比較 URL から取る。** 推測して URL を組み立てない。Chrome で mj を読むときは最終報告2行目の URL を使う。指示文にブランチ名を書くときも同じ。
  mj-logs にログが無いときは、Claude Code に `git log --all --grep=<Chat-Ref> --oneline` で到達を確かめさせ、ブランチ名とログの URL を返させる
- 貼られた `## 報告` には Chat-Ref の行が無い。「ログ:」の URL に含まれる Chat-Ref とブランチ名でどの指示の報告かを見分け、
  見分けられないときは中身を読む前に平野さんに確かめる（Chat-Ref の行は最終報告の最後の行だけ、#419 (b)）

### GitHub のファイルを読むとき（チャット側で確認済みの挙動）

- **raw 表示か、blob 表示（Markdown を描画した表示。`?plain=1` を付けない）を開き、get_page_text で本文全体を取る。**
  40KB 台のファイルも1回で取れている
  - raw 表示: `https://github.com/retroeater/mj/raw/<ブランチまたはSHA>/<パス>` を開くと、トークン付きの raw.githubusercontent.com に移動する
  - **`?plain=1` 付きの blob 表示では、get_page_text はファイルのメタ情報しか返さない。**
    Markdown 以外のファイル（`.py` など）は、`?plain=1` を付けない blob 表示でもメタ情報（行数・サイズ）しか返らない
- **github.com を開いた状態の JavaScript から、raw を fetch できる。** 本文をチャットに返さず、統計や一部分だけを返せる
- **javascript_tool の戻り値は長いと切り詰められる。** 上限は一定でなく、約1,000字で `[TRUNCATED]` になったことがある
- **`?` `&` `=` を含む出力はブロックされる。** 返す前に別の文字へ置き換える
- **重い処理は打ち切られる。複数ファイルを回す処理は書かず、1回の操作では1ファイルだけを扱う。**
  複数ファイルを連続で fetch した直後に、次の操作が4分のタイムアウトになった例が複数ある（因果は未確認）
- ブランチの検索は `https://github.com/retroeater/mj/branches/all?query=<語>`
- **Issues の検索結果の一覧は get_page_text では取れない。** JavaScript で `[role=listitem]` の中のリンクを拾う
- **ブランチ名で開いた内容は最新とは限らない。** 「未反映」と判断する前に、コミットSHA指定で開くか Claude Code 側に確認してもらう
  （ブランチ名で開いて、push 済みの変更を「未反映」と誤報した例が2回ある）
- **変更の前後を読み比べるときは、コミットの差分（`https://github.com/retroeater/mj/commit/<SHA>.diff`）を開いて get_page_text で読む。**
  比較ページ（`/compare`）は差分が読み込まれず、コミットの一覧しか取れない

代わりの手段（上の方法で読めないとき）:

- `?plain=1` 付きの blob 表示を開き、JavaScript で `#read-only-cursor-text-area` の `value` を読む。
  戻り値が切り詰められるため区切って返す。作業ログは末尾の `## 報告` 節から読むと速い
- **作業ログも、まず `?plain=1` を付けない表示 + get_page_text を試す。** `?plain=1` の画面で javascript_tool を使う読み方が
  続けてタイムアウトした一方、`?plain=1` なし＋get_page_text で読めた例も、逆に get_page_text が駄目で
  javascript_tool で切り出せた例もある。**どちらかが駄目ならもう片方を試す**
- **github.com を開いたタブの JavaScript から `/retroeater/mj/raw/<ブランチ>/<パス>` を fetch すると、ページの表示を待たずに中身を取れる。** work/ ブランチのログも読める
- **Claude for Chrome のタブのグループは、会話のターンをまたぐと無効になることがある。** URL を指定して開き直すほうが確実

### 確認用 URL

- **ログに確認用のプレビュー URL は無く、最終報告の画面にだけある**（非公開として扱う。CLAUDE.md「作業ログ」節）。
  work/ ブランチの見た目は、平野さんに最終報告の「確認用:」の行を送ってもらって見る。ログイン不要でスマホでも開ける。

## セッション識別子の確認（2026-09-16）

- **新しいセッションで最初の識別子（Chat-Ref の `XX`）を決める前に、ブラウザで
  https://github.com/retroeater/mj/tree/cloudflare/docs/logs の一覧を1回見て、`XX` が使われていないことを確かめる。**
  `XX` は日付をまたいで同じセッションが使い続けるため、`MMDD` を問わず `CHAT-*-XX-*` が無いことを見る
  （CLAUDE.md「Chat-Ref」節）
- ブラウザの操作は上の「1回まで」に従う。**タイムアウトしたら、チャット側の確認を省き、受け手側の確認（そのセッションの最初の指示で Claude Code が
  行うコミットと `docs/logs/` 履歴の確認、CLAUDE.md「Chat-Ref」節）に委ねてよい。**（受け手側の確認が本命）
- この一覧は `cloudflare` にある現在のファイルだけで、未マージのブランチのログや、マージ後に削除されたログは載らない。
  見落としは受け手側の確認で拾う

## Claude Code とのやり取り（2026-09-13〜）

- **Claude Code の完了報告は、平野さんが最終報告の「ログ（公開）」の行を送るだけにする。** チャット側はそのログを読む（上の「作業ログの読み方」）
- 一覧の出力など単発の確認でも、ターミナルに出すだけにせず、必ず作業ログに書かせる
- **ログは `## 報告` だけで足りる。** ログ全体を平野さんに貼ってもらうのは、チャット側が「報告だけでは判断できない」と明示して頼んだときに限る
- **平野さんが「申送り」と言ったら**（2026-09-16の指定）、チャット側は、振り返りで得た知見のうち今後の開発に役立つものを、issue の起票・追記や handover などの資料への追記で書き残す指示文を Claude Code 向けに作る。
  **申送りの指示では、追記先の残り容量を測らせ、規則だけを書かせる**（事例は archive へ。追記先が膨らむため）

## 指示文を書くときの注意（2026-09-16）

受け手側（Claude Code）が守るルールは CLAUDE.md「Chat-Ref」節。指示文を書く側は次を守る。雛形は `docs/instruction-template.md`。

### 書く前に実物で確かめる

- **会話の記憶から事実を断定して指示文に書かない。** 前回の報告・推測も同じで、根拠にしない。
  issue・ログ・ブランチの状態や数値は、Claude Code に `gh issue view` / `git log` で実態を確かめさせる。
  **書いた事実が怪しいときは、指示文を「〜を確かめ、食い違えば止まる」の形にする**
  （受け手側は前提と実物が食い違えば中断して報告する。CLAUDE.md「Chat-Ref」節）。
  **他のセッションが同じ日に変えている領域（`title/` など）を前提にする項目も同じ形で書き、
  受け手に使う直前にもう一度確かめさせる**（書く時点の確認では、書いた後に変わる分を拾えない）。
  **前の指示の前提を写すときは、変更の範囲（対象ファイル）が同じかを確かめ直す**
- **指示文を書く前に、対象・関連する issue の状態（Open/Closed・本文・コメント）を実物で確かめる。
  確かめられないまま、その issue の作業の指示を書かない。**
  ブラウザが使えないときは、書く前に平野さんに issue ページの PDF などを頼む
  （事例は `docs/notes/handover-archive-2026.md` の同じ見出し）。場面ごとに次も確かめる:
  - 最初の指示: 関係する issue の本文・コメントと、未マージの work/ ブランチの状況。
    既存の仕組み（テストの置き場所など）が「ある」ことも確かめる
  - マージ・クローズの指示: issue の Open/Closed と比較ページ（`/compare/cloudflare...<ブランチ>`）を1回確かめる。
    別のチャットセッションが並行して進めていることがあり、前回の報告だけを前提にしない
  - 複数の指示にまたがる作業: 最初の指示で、作業全体の論点について関連する issue（クローズ済みを含む）を
    Claude Code に洗い出させる。チャット側のブラウザでの検索は補助にとどめる。検索語には、変える対象そのものの語を入れる
  - 運用ルールや文書整理の指示: 同じ論点の issue の決定をクローズ済みも含め確かめる。
    並行セッションが別issueで同じ論点を保留にしていることがある（#328）
  - インフラやデプロイに関わる提案: クローズ済みの issue と実物の設定を確かめる。
    構成は CLAUDE.md「構成」、設定の記録は `docs/notes/cloudflare.md`
- **触れる領域の資料を読んでから指示文を書く。** CLAUDE.md や docs/handover.md に運用ルールを追記・変更するときは
  追記先の節の現在の内容を読む（読まずに書くと、他セッションが先に入れたルールと矛盾する記述を追加してしまう、#313）。
  ある領域に触れる指示を書く前は、その領域の `docs/notes/` の最近の変更も読む（並行セッションが途中で規則を足すことがある）。
  **マージ・ブランチ操作・`/workspaces/mj`の操作を含む指示文を書く前には、CLAUDE.md「ブランチ運用」節を必ず読む**
  （handover.mdだけを読んで書くと、禁止している操作を指示してしまう、#313）。例: OGP 画像・`og:title`・カード表示の作業では `docs/notes/ogp.md`
- **確かめた場所（issue・ログ・スクショ・実測）を正しく書き、見ていない出典を書かない。解釈を事実として書かせない**

### 平野さんの判断とマージの許可

**平野さんは指示文を読まずに貼る。** 本文に「違えば貼る前に教えて」と添えても、読み落とせば未決のことが判断として記録される。
次（欄を足す提案も含む）はいずれもこの前提から出ている。

- **指示文に「平野さんの決定」として書く内容は、実際に判断をもらってから書く。**
  現状維持（「〜は変えない」）も同じで、明示が無ければ「決定」ではなく「前提」の欄へ（欄は `docs/instruction-template.md`）。
  **チャット本文にも同じ内容を書き、日付は判断した日にする**（Chat-Ref の日付〈会話の開始日〉ではない）
- **マージの事前許可を書くときは、プレビューの確認が済んだことをチャットで平野さんに確かめてから書く。**
  「貼った＝プレビューを見た」とみなさない
- **チャット本文で「添付した」と書く前に、ファイルを作って提示し終えていることを確かめる。** 添付漏れに気づく負担が平野さんにかかる
- **公開など取り消しにくい段階の指示は、作る前に実施の時期を平野さんに確かめる。** 準備が整っていても、公開の時期は平野さんが決める
- **Claude Code の報告にある「〜は読み取れない」「〜は不明」を平野さんに伝える前に、会話の冒頭で読んだ handover と突き合わせる**

マージの許し方:

- **平野さんがマージの判断を済ませている小さな変更は、「平野さんの判断で、確認が済んだら cloudflare へマージしてよい」を同じ指示に含めてよい。**
  確認の基準を指示文に明記する。マージだけの指示を別に出すと1往復増える。
  受け手側の扱いは CLAUDE.md「ブランチ運用」のマージ基準にある例外（事前のマージ許可）
- **マージを事前に許せず「判断待ち」で止める指示を出したら、その報告を確認した返答に、マージ用の指示文を添える。**
  平野さんがセッションに口頭で「マージしてよい」と伝える前提にしない。マージ用の指示文には、同じ作業ブランチを続けて使うこと、
  マージで動く自動処理の見込み、止めた指示のログの状態を実態に直すこと、作業ブランチの片付けを含める
- **片付けは、関係のない検証（ワークフローの実行結果など）の成否に条件づけない。**
  検証が落ちると、ブランチ自体に問題が無いのに片付けまで止まり、指示が1本増える

### 指示文の書き方・渡し方

- **指示文にブランチ名を具体的に書かない。** 作業ブランチの名前は「『ブランチ運用』の規則どおり」と書く
  （具体名を書くなら、同節を読み直してから書く）。未マージのブランチとの重なりを確かめさせるときも名指しで挙げず、
  受け手に `git branch -r --no-merged origin/cloudflare` で一覧を出させてから確かめさせる
  （CLAUDE.md「Chat-Ref」の0章ゲートと同じ。名指しだと、指示を書いたあとに増えたブランチを見落とす）。
  既存ブランチを続ける指示は `docs/instruction-template.md`「作業ブランチ」の行
- **指示文にコミットSHAを固定して書かない。** 書いた時点のSHAは貼られた時点で古くなっていることがある。
  土台や比較対象は「その時点の`origin/cloudflare`」と書く。**既存の特定コミットを参照する場合（`git show <sha>:<path>` など）は書いてよい。**
  `docs/notes/branch-operations.md`「ブランチを削除するとき」の受け手側規定と対になる送り手側の規定（#313）
- 未マージの試作ブランチを捨てさせる場合は、CLAUDE.md の「未マージのブランチは削除しない」の例外であることを指示文に明記する
- **貼った指示文が途中で切れて届くことがある。** 指示文の0章に
  「ログの『指示』欄の末尾が、この指示文の末尾（最後の章の最後の行）と一致しているか確認し、一致しなければ作業せず報告する」を入れ、
  最後に途中切れを確かめる確認文を置く（文面は `docs/instruction-template.md`）。
  チャット側もログを読むとき、「指示」欄の末尾が送った指示文の末尾と一致しているかを確かめる
- **1本の指示に項目を詰め込みすぎない。3項目程度までにする。** 4〜5項目あると、途中で止まったときに何が済んで何が残るかが分かりにくい
- **配った後の指示を直すときは、先に平野さんがもう貼ったかを確かめる。** 貼った後に直した版を渡すと、同じ Chat-Ref の指示が2つの版で走る。
  貼った後なら新しい番号で出し直す（受け手側の重複の確かめ方は CLAUDE.md「Chat-Ref」節）
- **並行して走らせる指示の中で、ほかの実行中の指示の進み具合に触れない。** 書いた時点の「調査中」「未マージ」は、貼られた時点で古くなっている。
  ほかの指示の結果が要るなら「`<Chat-Ref>` のログの `## 報告` を読み、完了していなければ止まる」の形にする
- **既定モデルは Sonnet 5。別のモデルが要るときだけ、指示文の手前のチャット本文で伝える**（指示文に「推奨モデル」欄は入れない）。
  目安は haiku＝判断を伴わない確認・出力／sonnet＝既定（範囲が決まった編集・マージ）／opusplan＝調査・設計を含む最初の指示、
  複数指示にまたがる洗い出し、文書整理の判断。`/model` は既定として保存されるため、既定以外は `claude --model <値>` で起動する
  （ピッカーで `s` ならそのセッションだけ）。haiku でも共通手順とログは省かない

### 止まる条件と検証の指定

- **「差分が N 行ならマージ」のような止める条件は、先に変更対象がどこで使われているか（参照箇所）を調べさせてから決める**（容量の増減も実測を報告させる）
- **生成物を含む変更のマージの基準は、「差分は目的の行だけ」にせず、差分を種類に分けて許す範囲を決める。**
  スプレッドシートが正本のページは、再生成のたびにシートの変化が混ざる。許す差分の種類を列挙し、
  それぞれの確かめ方（変わった画像 URL は HTTP で 200 を確かめる、など）を書き、それ以外が出たら止める
- **スプレッドシートを読む指示には、行数の止まる条件を入れる。** 「行数が想定と違う・読み直すたびに変わる（貼り替えの最中の可能性）ときは、
  件数を書いて止まる」。平野さんが大量に貼り替える作業の後は、貼り終えたことを伝えてから読ませる
  （詳細は `docs/notes/static-generation.md`「生成を止める条件の設計」）
- **画像やページから値を読み取る処理を指示するときは、元の資料に何が書かれていて何が書かれていないかを明記する。**
  読み取る項目ごとに、資料に書かれている値か、こちら側（ページの見出しなど）が持っている値かを分けて書く
- **確認の指示に「通知が出ること」を書く前に、その通知が出る条件を報告で確かめる**（「変化が無いときは通知しない」設計だと確かめようがない）
- **ログの計測値や事実を issue に書かせるときは、チャット側の要約を渡さない。**
  「どのログのどの節から引用するか」を指定し、受け手に抜き出させる

### 見た目の決め方

- **見た目の検討は、文章で往復せず実物で見比べる。** 比較画像や実装を見るまで決まらず、決まった後も実物で変わる
- **見た目の案が2つ以上あるときは、最初から両方を実装して切り替えられる形にし、実物で見比べさせる。**
  切り替えは URL パラメータではなく、ページ内のラジオボタンでその場で切り替えられる比較ページにする（平野さんの指定）。
  **採用後は使わない案のコードとラジオボタンを消す。** 比較ページは noindex・どこからもリンクしない・sitemap に載せない形にし、決まったら消す
  （作り方は `docs/notes/title-pages.md`）
- 見た目の判断が要る作業は、試作 → 画面イメージ → 平野さんの判断 → 本実装 → マージ の順に指示を分けると手戻りが少ない
- **規則から値を決めた場合（「基準ちょうどの値」など）も、実装の前にその値を含めた見本を平野さんに見せる。**
  規則を満たすことと、見た目として受け入れられることは別
- 見た目から断定しない（サムネイルに焼き込まれた文字を、ページの意匠と取り違えた例がある）
- **コントラスト比などの数値は、手計算せずコードで計算する。** 計算式（WCAG 2.x の相対輝度など）を明示して
  Claude Code にも計算させ、突き合わせる

### 外部サービスの設定

- **最初の調査の指示に「権限・共有・組織ポリシーの制約」を洗い出す項目を入れる**
  （サービスアカウントが組織外の扱いになり、管理コンソールでの設定が要ることがある）
- **実装を指示するときは、その洗い出しをもとに、要る Secret・変数・共有をすべて列挙する**
- **設定の変更を平野さんに頼むときは、選択肢の意味を頼む前に公式ドキュメントで確かめる。** 名前から推測しない
- **検索を止めうる変更は、疑いが出た時点で確かめる。後日の確認に回さない**

## ほかのセッションへの共有（2026-09-17）

- **宛先は相手の「チャット」にする。** 相手のチャットが自分の Chat-Ref を付けた指示文に書き直してから、Claude Code に渡す
  （相手の Claude Code に直接渡る文面にすると、作業ログが残らない）
- **「ログにこう書いてある」と「確かめた事実」を分けて書く。** 解釈を事実として伝えると、相手がそれを前提に動く

## コミット履歴を独立に検証するとき（2026-09-13、#211）

チャット側がコミット履歴を独立に検証する必要が出た場合は、Claude Code 側（Codespace）で書き出し、平野さんがチャットにアップロードする。

- 通常（軽量、85KB程度）: コミットグラフのテキスト書き出し。
  親子関係・祖先判定・Chat-Ref の到達確認・変更ファイルと行数を追える

  ```
  git log --all --pretty='COMMIT|%H|%P|%ci|%s' --numstat > /tmp/graph.txt
  ```

- 深掘りが必要なとき（64MB）: 分割バンドル。3ファイルをアップロードし、
  チャット側で `cat` 結合して clone する

  ```
  git bundle create /tmp/mj.bundle --all
  split -b 22m /tmp/mj.bundle /tmp/mj.bundle.part-
  ```

  `--filter=blob:none` や `--since` を付けたバンドルは軽いがクローンできない
  （検証済み）。使わないこと。
